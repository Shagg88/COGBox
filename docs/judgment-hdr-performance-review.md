# Judgment native HDR performance review

Reviewed the local native-HDR changes and Judgment runs `20261116-103841`, `112535`, `113237`, `113556` and `113710` on 2026-11-16. This review does not establish an exact FPS regression: routes/cameras differ, and some runs use SMAA while others use DLSS Quality. The first candidate later became native in gameplay too, so its entire log is not a reference-only baseline.

## Most likely steady costs

1. **Two scene executions.** The renderer retains the original scene draw, then replays the grading program into FP16. The HDR shader still executes the original decode/DOF/bloom/grading path to retain the original bounded reference, before its additional highlight extension. This repeats full-screen scene work. See `shadow_renderer.cpp` around `NativeHdrDraw` and the original `issue(target, 0)` at the draw tail.
2. **Highlight work on diffuse pixels.** `JudgmentSceneSource` computes extended neutral grading, LUT continuation, highlight boost and PsychoV35 before `NativeUe3MapExtendedGrade` mixes with the original grade. That mix has zero HDR weight when all captured exposed RGB components are at most 0.5. Explicitly avoiding the extended calculation there is a promising exact-output optimization; verify generated shader control flow and output equality before installation. Zero fade and a black original grade are additional candidates, subject to matching the mapper's exact behavior. The continuation path performs up to five tetrahedral LUT evaluations, four texel loads each (20 loads), plus gamma conversions, curve evaluation and hue/gamut math. This is a source-level cost analysis, not a GPU time attribution.
3. **A second FXAA execution and conversion.** Each consumed native scene version requires a linear-to-encoded FP16 compute pass, then a replay of the original FXAA shader into linear FP16, followed by the original bounded FXAA draw. The latest DLSS log records 10,853 effect replays and 10,853 encodes, with one 63 MiB proxy. Reuse across versions works, but the scene changes each frame, so reuse cannot remove its per-frame conversion. The high-quality FXAA permutation is a substantial branching/filtering program; it is not a simple blit.
4. **Additional storage/bandwidth.** At 3840x2160 visible resolution, automatic stencil-compatible HDR composition allocates a padded 3840x6144 FP16 scene: 180 MiB. The visible effect proxy is 63.28 MiB. SMAA adds a visible FP16 output of another 63.28 MiB (about 306.6 MiB total additional scene/proxy/AA storage with SMAA). The encoder processes visible rows only. Unused padded rows consume residency, not a full extra per-frame copy. A single proxy encode logically reads and writes about 126.6 MiB per frame before FXAA traffic. Do not assume this alone is the main bottleneck; no memory-pressure diagnosis has been established.

## What the logs do and do not show

The latest reviewed DLSS Quality run is `20261116-113710`: scene rendering at 2560x1440, output 3840x2160, HDR peak 3800 nits. Native grading/effect transport is still observed at 3840x2160. In its last ten GPU batches the median recorded total is approximately 9.67 ms and draws 5.16 ms; the older DLSS run's last ten batches are about 8.34 / 3.84 ms. These are different sampled scenes, so the difference must not be reported as a measured 1.33 ms HDR regression.

Proxy allocation stays at 63 MiB and `EffectAllocation` returns the existing allocation for unchanged dimensions. Recent descriptor-ring and upload-ring wait counters are zero. Thus repeated proxy allocation or ring exhaustion is not supported by these samples. Renderer optimization counters remain active: texture memo reuse, ownership fast paths, constant upload avoidance and fill-transfer skips were not disabled by this patch.

Both FXAA variants have initial pipeline-preparation misses. One later generic driver pipeline build took 48.9 ms on a worker; that is not proof of a 48.9 ms render-thread stall or of an HDR-specific pipeline. Shader preparation does not fully pre-create every state-specific graphics pipeline. This is relevant to first-visit hitches, not by itself an explanation for a sustained FPS drop. DevKit snapshot/readback captures can also disturb individual frames and should be excluded from performance comparisons.

## Recommended order

First, measure the native grading, proxy conversion and FXAA replay separately during an equivalent warmed gameplay route, without DevKit capture/readback during timing. Add and validate an early diffuse/black/fade path for Judgment; preserve the original grade, peak fitting, alpha luma and fade exactly. Uniform grading-curve terms could also be prepared once when their source constants change rather than recomputed for every pixel, provided numerical behavior remains within an explicitly checked tolerance.

Next, investigate one scene draw with two outputs: original bounded RGBA8 and linear FP16. The HDR shader already retains the original grade, so this may remove the duplicate original scene execution while preserving guest resolves, UI inputs and exposure behavior. This needs renderer/state validation; simply dropping the SDR draw would break those dependencies. A combined FXAA path would similarly need to preserve original edge decisions and both original and HDR samples, not clamp the filtered HDR result into a fake SDR reference.

Finally, investigate trimming padded HDR allocation while maintaining exact stencil geometry/target compatibility. Do not disable selective FXAA or the native companion to gain FPS: that would restore the SDR fallback this feature was added to prevent.

## Optimization candidate implemented

Judgment-only paired scene output now writes original encoded SDR and linear FP16 in one draw. A visible linear staging target avoids reading and writing the same HDR resource during the later paired FXAA draw. The original SDR resolve and its exposure/UI consumers remain intact. In the supported FXAA path, the original algorithm selects edges/UVs once; HDR samples are reconstructed from the linear staging texture with encoded-domain bilinear filtering. Both bounded SDR and linear HDR are emitted in the same draw. This removes the encoded full-screen conversion dispatch and the duplicate FXAA control program. Wrap/clamp linear single-level RGBA8 inputs are admitted; other states retain the validated replay fallback. Pending scene staging cannot be presented or treated as completed HDR by UI.

Dark diffuse pixels, a fully black grade and zero fade avoid unnecessary highlight reconstruction while retaining the existing mapper's result. This is a computation change, not a lighting/peak retune. `gowj_hdr_single_pass=false` selects the replay arrangement for comparison; the dark-pixel computation shortcut remains enabled. Gears 2/3 do not enable the new paired renderer path.

GPU checks pass on D3D12 and Vulkan for the captured scene/FXAA pipelines, both FXAA permutations, original SDR output, independent HDR filtering with original SDR edge decisions, R/B mapping, wrap/clamp addressing, peak/fade behavior and the scene's original SDR output. A half-alpha proxy can choose different edge branches at ties; the new direct path uses the original SDR alpha. Tests compare against an independent reference that makes those same original decisions. Small remaining HDR filtering differences are within FP16/filter precision tolerances. Manual interpolation currently uses 8-bit subtexel weights; the GPU comparisons cover the available backends on this machine, not every vendor's filtering precision.

Isolated D3D12 4K fixture benchmarks: old encode + SDR/HDR FXAA draws versus paired FXAA: 1.7420 -> 0.5718 ms (lighter permutation), 1.8645 -> 0.6232 ms (heavier permutation). This excludes scene grading, gameplay simulation and end-to-end frame pacing. It is not a measured whole-game FPS gain.

A separate live lighting capture before installation found peak linear luminance 3.62975 at 200-nit paper white (about 726 nits), with RGB above white and no nonfinite pixels. Thus the running build was not globally capped at the 203-nit UI level; particular materials/lights can still be near paper white. No lighting retune was made in this optimization.

## Installed candidate and first live check

Installed executable SHA256: `1A1219D89B76666ED0F38ACF9D743AD399A4ABD8977565068D9365DCA4C3A8FE`. Previous executable is preserved under `work/hdr-judgment-perf-20261116/before-install/20261116-120416/`. The SDK runtime DLLs were not changed for this optimization.

Run `20261116-120425` confirms both scene and FXAA paired paths execute. At the sampled gameplay point: 2,449 FP16 / 251 reference frames, 2,456 paired scenes, 2,438 paired FXAA draws. Legacy conversion dispatches held at 16 across later 300-frame batches, instead of growing once per gameplay frame. Both captured FXAA permutations incurred startup preparation fallback, then used the paired path. Reference frames also held steady across the sampled gameplay interval. Some menus/transitions still use the conservative reference path.

The old encoded proxy remains cached after those initial fallbacks. Its 63.28 MiB plus the 63.28 MiB linear staging texture are reported together as 126 MiB (within the 128 MiB selective budget). Therefore this candidate removes recurring conversion work, not the cached fallback allocation. Removing that allocation immediately would risk repeated allocation churn when unsupported effect states recur. Whole-game FPS/frame-pacing acceptance still requires the user's same-route comparison.
