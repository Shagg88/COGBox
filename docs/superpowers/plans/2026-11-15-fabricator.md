# The Fabricator Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** COGBox's mod store: a FABRICATOR screen in the launcher (Library, Store, Creator) backed by new routes on
the COGBox master server, with moderation in the admin panel.

**Architecture:** The server side is a module in the master server (`tools/master-server/src/fabricator/`): its own
`fab_*` tables in the same SQLite database, files on the server's `/data` volume, routes under `/api/v1/fabricator`, and
admin calls on the existing loopback private API, which the admin panel uses. Big transfers stay off the event loop's
critical path: uploads arrive in 16 MiB chunks, downloads are streamed from disk with HTTP ranges. The launcher gets a
pure model (JSON, names, local checks, install bookkeeping), a transfer layer (WinHTTP, resumable), an install layer
(reusing the Mods tab's zip unpacking), and the screen.

**Tech Stack:** TypeScript / Fastify 5 / better-sqlite3 (FTS5) / vitest; `yauzl` (zip reading), `yazl` (test zips),
`sharp` (screenshots); C++17 / Dear ImGui / SDL3 / WinHTTP / miniz / nlohmann JSON / stb_image (launcher, MinGW).

**Spec:** `docs/superpowers/specs/2026-11-15-fabricator-design.md` (agreed with KiltedKernel and Shagg, 2026-11-15).

## Global Constraints

- No mod file, screenshot or Microsoft asset is ever committed to the repository, in tests or anywhere else: test zips
  are built by the tests from generated bytes.
- No token, uuid, player address or file path in any log line: new routes follow `src/log_scrub.ts`.
- All limits are settings (Task 1), filled in by Shagg; the values below are only the starting defaults.
- Starting defaults: 4 GiB per file (packed), 8 GiB unpacked, 50 000 files, 20 GiB per creator, 3 uploads per
  creator per day, server-wide daily cap 50 uploads and 100 GiB, account at least 3 days old to publish, last 3
  versions' files kept, uploads refused above 85% disk used, 16 MiB chunks, upload sessions expire after 24 h,
  30 download addresses per account per hour, download addresses valid 15 min.
- Refused file types inside a mod: `.exe .dll .xex .xexp .bat .cmd .ps1 .vbs .js .msi .scr .com .lnk`.
- Screenshots: 1-6 per mod, PNG or JPEG, at most 4 MB and 3840x2160 each, re-encoded by the server (metadata gone).
- Text limits: name 3-60 characters, short description up to 120, description up to 8 000, up to 8 tags of up to 24
  characters, version text up to 24, "what's new" up to 2 000.
- Games: `gears1`, `gears2`, `gears3`, `judgment`. Types: `texture_pack`, `campaign`, `gameplay`, `visuals`, `audio`,
  `other`. Report reasons: `malware`, `stolen`, `broken`, `offensive`, `other`.
- A store install's folder holds `fabricator.json`; an update moves the old folder to
  `<Game>\mods\.fabricator-backup\<folder>` (one kept per mod).
- Launcher code is C++17 (MinGW `build.sh` flags), the style of `mods.cpp` / `social_net.cpp`; server code follows
  `src/social/*.ts` (plain functions taking `db`, routes as Fastify plugins).

## Review Focus

- An upload interrupted mid-chunk, or across a server restart, resumes where it stopped (Task 4: `resumes after a
  restart`).
- A download cut off part-way resumes with a range request, and a file whose SHA-256 is wrong is discarded and never
  unpacked (Task 6: `range requests`; Task 10: `bad hash is not installed`).
- Updating a mod the player edited by hand keeps the edited copy in the backup folder (Task 11: `update keeps the
  old folder`).
- A mod name with characters Windows forbids, a reserved name (`CON`, `NUL`...), or one that matches a folder already
  in `mods\` gives a safe, distinct folder (Task 9: `folder names`).
- A taken-down mod vanishes from the store and its downloads stop, while players' installed copies stay and show
  "Taken down" (Task 6: `taken-down mods`; Task 12: Library pill).
