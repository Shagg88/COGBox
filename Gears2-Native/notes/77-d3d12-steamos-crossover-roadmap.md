# COGBox D3D12-first roadmap for Windows, SteamOS / Proton, and macOS / CrossOver

**Prepared:** 2026-10-28  
**Updated:** 2026-10-28 — graphics API work is ranked first; expanded DLSS/FSR diagnosis with current AMD/NVIDIA guidance and COGBox-specific temporal-input, exposure, scaling and per-title validation.  
**Purpose:** Set a ranked work plan for making COGBox's existing D3D12 renderer smooth and dependable on Windows, especially SteamOS / Steam Deck, while adding high-priority compatibility evaluation for macOS / CrossOver. This report focuses first on using the Windows game executables through their compatibility stacks. It does not propose further work on COGBox's own Vulkan renderer until the D3D12 gates below pass.  
**Source review:** Local Gears2-Native source, build setup, launcher settings, project notes and runtime patches were checked against current primary documentation from Valve, vkd3d-proton, Microsoft, CodeWeavers, Apple, AMD GPUOpen and NVIDIA. No game source files were changed.

## Executive recommendation

Make the first engineering goal **the existing Windows D3D12 game build running through current Proton on SteamOS**, with COGBox's own API selection explicitly forced to D3D12 for diagnostic builds. Proton implements Direct3D 12 with **vkd3d-proton translating D3D12 to Vulkan**. That still requires SteamOS's Vulkan loader, Mesa/RADV driver and Vulkan hardware features, but it does **not** require COGBox's own Vulkan backend, shader translator, or Vulkan presentation path. Keep that distinction clear in code, settings, logs and support instructions. [vkd3d-proton overview and requirements](https://github.com/HansKristian-Work/vkd3d-proton#vkd3d-proton)

There is already a concrete local blocker to this investigation: `Gears2-Native/cogbox/src/gears_settings.cpp` computes `vk = s.i("Api") == 1 || env.wine` and therefore launches the game's Vulkan path whenever Wine/Proton is detected, even if the player selected DirectX 12. The project's 0.2.2 priority note says this was added after a Steam Deck D3D12 launch exited with code 3, while a SteamOS desktop with a newer AMD GPU did start D3D12. That makes D3D12-on-Proton **setup-sensitive and unproven on Deck**, not inherently impossible. First create a safe, explicit D3D12-under-Proton test path; then find the exact init failure and fix it.

The strongest local compatibility leads are the bundled Microsoft Agility SDK (`D3D12Core.dll`, SDK version 614 and app exports), COGBox's strict Shader Model 6.6 device check, the optional programmable-sample-position path, the rexglue DXGI presenter features (frame-latency waitable object, tearing, and swap-chain behavior), and the renderer's currently conservative occlusion-query behavior. All are testable. None should be called the root cause of issue #15 before a forced-D3D12 Proton log identifies the failing step.

macOS / CrossOver is a second high-priority compatibility target, but it is a distinct graphics stack. CrossOver's D3DMetal option translates Direct3D 11/12 through Apple's Game Porting Toolkit to Metal; CrossOver's DXVK option is for Direct3D 10/11 and is not a substitute for COGBox's D3D12 renderer. The current CrossOver 26 changelog reports D3DMetal 3.0; use the latest stable CrossOver build in the test matrix and record its exact version. [CrossOver graphics backends](https://support.codeweavers.com/advanced-settings-in-crossover-mac?kb_language=en_US), [CrossOver changelog](https://www.codeweavers.com/crossover/changelog). The local launcher currently treats every Wine environment alike and forces COGBox's Vulkan backend, so it will not naturally test COGBox D3D12 through D3DMetal. A dedicated CrossOver/Apple Silicon evaluation must first establish which renderer is actually loaded and whether COGBox's Agility SDK 1.614, Shader Model 6.6, DXGI presenter and required D3D12 features are implemented by that CrossOver/D3DMetal version. This is a compatibility hypothesis, not an established working path.

## The layers involved

On a Steam Deck, a Windows COGBox port launched by Steam is still a Windows executable. Proton supplies the Windows compatibility environment. For D3D12, vkd3d-proton supplies the D3D12/DXGI-facing compatibility implementation and converts the game's D3D12 workload to Vulkan calls; SteamOS's Linux Vulkan driver then talks to the AMD GPU. The chain is approximately:

```text
COGBox Windows port (D3D12 API)
  -> Wine / Proton D3D12 and DXGI implementation
  -> vkd3d-proton
  -> Vulkan loader + SteamOS Mesa RADV
  -> Steam Deck AMD GPU
```

This is the requested D3D12-first plan: fix and ship one D3D12 renderer path that runs natively on Windows and through Proton. The COGBox Vulkan backend remains a separate renderer/backend implementation and can stay deferred. Proton's D3D12 translation necessarily uses Vulkan underneath; that is part of the operating system compatibility layer, not a request to advance or enable COGBox's Vulkan renderer.

Static recompilation does not bypass this compatibility stack. It makes the original guest game code native host code, but the port still depends on its host runtime, Windows APIs, D3D12 calls, DXGI presentation, SDL input, filesystem and audio. The GPU layer is a standard Windows D3D12 application from Proton's point of view, so standard D3D12 translation is a plausible route. The full game still needs end-to-end testing because kernel/runtime and controller behavior are outside the GPU translation layer.

## What the local COGBox project currently tells us

### Evidence of a D3D12-on-Proton workaround, not a completed D3D12 path

- `Gears2-Native/notes/76-priorities-0.2.2.md:5-31` explicitly ranks D3D12 on SteamOS / Deck first. It records issue #15's Deck process exit code 3 shortly after renderer startup and a separate report where D3D12 did start on SteamOS desktop with an RX 9070 XT. It lists Agility, feature level/capabilities and DXGI presentation as **suspects**, not proven causes.
- `Gears2-Native/cogbox/src/gears_settings.cpp:649-656` forces the game's Vulkan path under Wine/Proton regardless of the selected D3D12 setting. As a result, ordinary launcher runs on SteamOS do not currently test the requested D3D12 path.
- The same launcher code suppresses exclusive fullscreen and the D3D12-specific frame generation / low-latency integrations under Wine. Borderless/compositor-owned presentation is the sensible initial baseline; feature parity should be added only after startup and frame pacing are stable.
- `Gears2-Native/src/layer0_xenos/renderer/d3d12_backend.cpp:1202-1241` creates a D3D12 feature-level 12.0 device, rejects the device unless Shader Model 6.6 is reported, and queries optional stencil-reference and programmable-sample-position features. A Windows GPU that works does not prove vkd3d-proton will report the same support or behavior.
- `Gears2-Native/src/layer0_xenos/agility/agility.cpp:1-9` exports `D3D12SDKVersion = 614` and `D3D12SDKPath = ".\\D3D12\\"`. `Gears2-Native/CMakeLists.txt:134-144` copies the Agility SDK's Microsoft `D3D12Core.dll` to each game directory. `cogbox/tools/package_cogbox.ps1:43,125-126` requires and includes it in every game's release folder. This is a significant Proton compatibility boundary that needs a deliberate A/B, not a silent assumption.
- `Gears2-Native/patches/rexglue-sdk.diff:4014-4064` adds a DXGI frame-latency waitable swap chain and tearing support to the shared presenter. The patch waits on the frame-latency handle and reports when the handle or latency setup fails. Validate this presentation path under Gamescope rather than assuming Windows DXGI timing maps identically under Proton.
- `Gears2-Native/notes/30-tooling.md` says the D3D12 backend compiles runtime HLSL through FXC/D3DCompile and that local renderer debugging currently depends on Windows-oriented D3D12 tools. Windows measurements therefore cannot substitute for Proton logs, RADV measurements and Steam Deck frame-time captures.

### What existing evidence does *not* prove

- Exit code 3 does not identify whether failure came from D3D12 device creation, shader-model query, the Agility SDK loader, a missing optional feature, swap-chain setup, or another startup stage. The first fatal renderer log line and Proton/vkd3d logs are needed.
- The line `Vulkan instead of DirectX 12` in launcher notes means a normal Proton launch can appear to work while providing no evidence that D3D12 works there.
- A successful D3D12 start on a desktop AMD card does not establish Steam Deck support. Deck OS/Proton/Mesa versions, GPU capabilities, swap-chain surface and power limits differ.
- The local notes and issue logs identify other SteamOS symptoms, including Gears 2 network-layer initialization. Keep that separate from renderer startup unless a single trace shows a causal connection.

## Priority roadmap

**Ordering update:** Graphics API compatibility and integration now occupy priorities 0–7: D3D12 platform paths, Agility, capability checks, presentation/swap chain, upscaler/frame-generation APIs, shader/pipeline translation, Windows baselines, and the decision to defer COGBox's own Vulkan renderer. Player features and other implementation work follow those API gates.

### Priority 0 — make D3D12 testable and observable on SteamOS and macOS

**Goal:** Make COGBox's most mature renderer—the Windows D3D12 path—explicitly testable on both SteamOS/Proton and macOS/CrossOver, without advancing COGBox's own Vulkan backend. CrossOver is the compatibility environment; D3DMetal is its Direct3D 12-to-Metal route.

1. Replace the blanket `env.wine` renderer rule with an explicit platform/runtime choice. Keep safe defaults, but expose a developer/test override that can force COGBox D3D12 under both Proton and CrossOver. In CrossOver, enable D3DMetal for the bottle; do not confuse that with selecting COGBox's own Vulkan backend. Preserve a manual Vulkan fallback for diagnosis.
2. Log separately: requested API, launcher-selected API, game-created API, and any fallback. Include the compatibility environment (Proton vs CrossOver), graphics translation layer (vkd3d-proton vs D3DMetal), and actual loaded modules. Do not count a COGBox Vulkan run as a D3D12 test, even if the host compatibility layer internally uses Vulkan or the CrossOver bottle has D3DMetal enabled.
3. Make the failure path include the named stage and native HRESULT/status: provider creation, `D3D12CreateDevice`, shader-model query, optional feature query, adapter selection, Agility `D3D12Core.dll` resolution, DXGI factory/swap-chain creation, waitable-object creation, first `Present`, and first guest frame.
4. Retain platform logs even when a process exits quickly: Proton/vkd3d-proton logs for SteamOS, CrossOver bottle logs for macOS, plus COGBox logs. Include the exact port build/hash and game (TU/disc) so a log cannot be accidentally matched to another binary.

**Why first:** The launcher currently makes both experiments ambiguous: it forces COGBox Vulkan for generic Wine environments, which includes Proton and CrossOver. Without an explicit D3D12 path and clear backend/runtime logs, the Deck failure and Mac feasibility remain untestable. COGBox D3D12 is farther along than its own Vulkan backend, so both compatibility targets should begin with D3D12.

**Pass condition:** On SteamOS, logs prove the D3D12 provider/device path through Proton/vkd3d-proton; on Apple Silicon, logs prove the D3D12 path through CrossOver/D3DMetal. Each log names the first failing initialization stage if startup fails. Keep the test switch until all three games pass the same stated platform gate, with any title-specific exception visible in the matrix.

#### macOS / CrossOver track within this same top-priority D3D12 milestone

**Goal:** Determine whether the Windows COGBox launcher and all three game executables can run reliably on Apple Silicon through current CrossOver, and identify the least expensive supported route before committing to a native macOS renderer.

**Why this is a real opportunity:** Current CrossOver releases expose a D3DMetal backend for Direct3D 11/12 applications. CodeWeavers describes D3DMetal as a Game Porting Toolkit graphics translation layer and lists it separately from DXVK, which handles D3D10/11. Apple's current Game Porting Toolkit documentation also describes evaluating unmodified Windows executables on Apple Silicon and inspecting shader compatibility/performance. That makes the project's existing Windows D3D12 executable a reasonable first experiment; it does not mean every D3D12 feature used by COGBox is implemented or fast. [CodeWeavers' D3DMetal backend documentation](https://support.codeweavers.com/advanced-settings-in-crossover-mac?kb_language=en_US), [CrossOver changelog](https://www.codeweavers.com/crossover/changelog), [Apple Game Porting Toolkit](https://developer.apple.com/games/game-porting-toolkit).

**Project-specific blockers and uncertainties:**

- `Gears2-Native/cogbox/src/gears_settings.cpp:652-656` uses `env.wine` as the renderer decision: under any Wine environment it chooses COGBox Vulkan unless Vulkan was already selected. CrossOver is Wine-based, so the launcher will select Vulkan here too. The comment and message refer to Proton, but the boolean does not distinguish SteamOS from CrossOver/macOS.
- COGBox's D3D12 backend is compiled only under `_WIN32`; the non-Windows branch returns no D3D12 backend. The Windows executable can still run under CrossOver/Wine, but a native macOS build cannot use this backend as-is.
- The D3D12 renderer requires Shader Model 6.6 and loads a bundled Agility SDK `D3D12Core.dll` version 614. CrossOver/D3DMetal may support Direct3D 12 generally while still lacking a specific API, feature query, Agility runtime loading behavior, shader operation or DXGI behavior COGBox assumes. A successful launch of another D3D12 game is not proof for this custom renderer.
- The Vulkan backend is also not yet a proven Mac fallback. It dynamically loads `vulkan-1.dll` in Windows builds and requests Vulkan 1.3 with a set of renderer-specific features. CrossOver's Mac Vulkan implementation/translation and MoltenVK feature exposure must be measured against those exact requirements; do not assume a Windows Vulkan build works because a bottle has a Vulkan option.
- The launcher is a Windows `WinMain`/Win32 application even though it uses SDL3. Its install, update, file picker, registry/shell integration, drag-and-drop and relaunch behavior must be tested separately from the game executable. Start with direct game-executable launches to isolate renderer/runtime from launcher behavior.
- Apple Silicon runs Windows x86-64 instructions through an additional CPU translation layer. Measure CPU-bound recompilation/runtime costs separately from GPU translation, and define which Mac architectures and macOS/CrossOver releases are in scope. Recheck the CPU-translation dependency as Apple and CodeWeavers evolve Rosetta/CrossOver support. [CodeWeavers CrossOver requirements and OS matrix](https://www.codeweavers.com/crossover/), [Apple Rosetta documentation](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment).

**Recommended investigation sequence:**

1. **Set a narrow baseline.** Target Apple Silicon first (M1 or later) using a current stable macOS and CrossOver release that CodeWeavers supports. Record exact Mac model/SoC, macOS, CrossOver build, bottle architecture/Windows version, game build/title update, COGBox version and display mode. Treat Intel Mac as a separate track; do not claim support based on an Apple Silicon test.
2. **Test one game executable directly before the launcher.** In a clean CrossOver bottle, run the Windows game executable with its normal user-owned game data and a minimal configuration. Keep logs visible. Confirm that the process starts, loads a scene, presents frames, accepts a controller, writes saves and exits. This identifies game/runtime feasibility without conflating launcher installation and updating.
3. **A/B renderer backends deliberately.** With CrossOver's D3DMetal enabled, test a diagnostic build that can explicitly request COGBox D3D12 despite Wine detection. Separately test the existing COGBox Vulkan path only if its loader and required Vulkan feature set are present. Keep D3DMetal, DXVK and WineD3D terminology precise: DXVK is not a D3D12 route. Log actual backend, implementation module paths, device/API/features and the first failure. Never report D3D12 as active merely because CrossOver's bottle has D3DMetal toggled on.
4. **Instrument the exact D3D12 boundary.** Capture `D3D12CreateDevice`, Agility `D3D12Core.dll` resolution/version, Shader Model query, each required/optional `CheckFeatureSupport`, resource/format support, shader compilation and pipeline creation, swap-chain/factory creation and first `Present`. Compare these with a Windows D3D12 baseline. If the process exits, preserve the first error and CrossOver bottle logs before changing DLL overrides or graphics toggles.
5. **Validate all three titles only after one title reaches a stable scene.** Run the same startup/menu/gameplay/save sequence on Gears 2, Gears 3 and Judgment; exercise cutscenes, post-processing, occlusion, resolution changes, Alt-Tab/focus, sleep/resume, controller reconnect and long play. Shared renderer success in one game does not prove per-title shaders, formats, memory use or startup hooks match.
6. **Test launcher behavior as a separate milestone.** Verify launch, game selection, per-title data folder selection, path handling for macOS volumes/spaces, logs/problem-report packaging, updater behavior and returning focus to the launcher. If the Windows launcher is unreliable, publish a clear direct-launch workaround for testers while the launcher is made CrossOver-compatible; do not ask users to perform risky DLL overrides or copy Windows system files.
7. **Profile under realistic Apple hardware limits.** Capture CPU frame time, GPU frame time, memory pressure/unified-memory use, thermal behavior, shader-cache cold/warm behavior and sustained frame pacing. Test internal and output resolution separately. Disable frame generation, Reflex/Anti-Lag and D3D12-only upscalers until their runtimes and input paths are independently verified on CrossOver; document unsupported options rather than silently falling back.
8. **Define go/no-go criteria.** If COGBox D3D12 works through D3DMetal with acceptable stability and performance, make this a documented CrossOver compatibility target with a versioned test matrix. If it fails on unsupported D3D12 features or runtime integration, file a minimal reproducible compatibility report and evaluate the native macOS renderer route below rather than accumulating undocumented Wine DLL overrides.

**Especially relevant related project:** The public [Gears3-Azura project](https://github.com/Carolux97/Gears3-Azura) describes a native macOS Apple Silicon and Linux static recompilation of Gears of War 3 using ReXGlue. Its README says macOS rendering uses a Metal backend while Linux/Windows use Vulkan, and that users provide their own game dump. This is direct evidence that the same title and recompilation ecosystem are being taken to macOS, but it is a *native Metal port*, not evidence that COGBox works in CrossOver or that COGBox can reuse its renderer. Its published license restricts redistribution/modification; use public design notes and compatibility observations as research, and obtain permission before reusing code or patches. This should be a parallel fallback/benchmark investigation, not a reason to abandon the requested CrossOver path. [Gears3-Azura README and platform notes](https://github.com/Carolux97/Gears3-Azura).

Other Xbox 360 recompilation projects can demonstrate that host-platform ports are feasible, but their platform list alone does not prove CrossOver compatibility. For example, projects built on ReXGlue advertise Windows/Linux/macOS or Apple Silicon targets; that generally means native host builds/backends, not necessarily Windows builds running in CrossOver. The design lesson is to separate CPU guest-code recompilation, OS/runtime shims and the renderer backend, then validate each layer on Mac. Do not describe CrossOver as an Xbox 360 emulator: it runs the already recompiled Windows host executable and translates its Windows APIs/graphics calls.

**Pass condition:** On a clearly stated CrossOver/macOS/Apple Silicon baseline, at least one title launches through gameplay using a positively identified renderer, passes sustained play/save/reload/exit without fatal graphics errors, and reports actual feature fallbacks. All three titles and the launcher then pass their own checklist before public support is claimed. Otherwise label CrossOver experimental and publish the exact failing stage plus the native Metal comparison as the next route.

**Research sources:** [CodeWeavers CrossOver graphics backends](https://support.codeweavers.com/advanced-settings-in-crossover-mac?kb_language=en_US), [CrossOver release changelog](https://www.codeweavers.com/crossover/changelog), [CodeWeavers CrossOver system/OS compatibility matrix](https://www.codeweavers.com/crossover/), [Apple Game Porting Toolkit evaluation and shader tools](https://developer.apple.com/games/game-porting-toolkit), [Apple Rosetta translation constraints](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment), [Gears3-Azura native macOS ReXGlue port](https://github.com/Carolux97/Gears3-Azura).

#### Cross-title parity gate — all three games advance together

Apply this gate to shared renderer, launcher, runtime, platform and performance work. Maintain one matrix with a row for **Gears of War 2**, **Gears of War 3** and **Gears of War: Judgment**, and columns for Windows D3D12, SteamOS/Proton D3D12 and macOS/CrossOver D3D12. For each cell record the exact game/TU build, launcher/runtime build, actual renderer, boot/menu/gameplay/save-reload/exit status, stable cap and frame-time results, major graphics features, controls, known defects, and whether the result is tested, limited, blocked or unsupported.

1. Make the same release gates apply to each game: clean launch, title menu, representative campaign gameplay, checkpoint/load, save and reload, sustained session, resolution/graphics changes, controller and keyboard/mouse basics, clean exit and useful logs. Run the relevant test on every title after shared renderer/runtime changes; a single-game result is not a shared-layer pass.
2. Compare performance using controlled scenes and identical host settings where possible. Do not require numerically identical FPS across different scenes; require each game to meet the same advertised cap/quality policy on the same declared hardware, and investigate any title whose p95/p99 frame time, recurring hitch rate, crash rate or input latency materially lags the other two.
3. Keep feature status explicit per game. If DLSS, FSR, frame generation, HDR, a post-process option, input mode or a platform backend does not work in one title, mark that cell as limited/unsupported and either fix it or clearly disclose the exception. Do not let a launcher-wide toggle imply that all three games support it.
4. Make release/support claims from the weakest game's verified result for the stated platform and feature set. If one title falls behind, keep that gap at the top of the next sprint and avoid describing the whole three-game collection as having the same support level until the matrix is brought back into parity.

**Parity pass condition:** All three titles meet the same core launch, sustained-play, save/reload, input and exit gates on every platform advertised as supported. Shared feature availability and performance differences are either resolved or clearly listed per game; no aggregate “all games supported” status hides a failing title.

### Priority 1 — isolate Agility SDK loading from Proton's D3D12 runtime

**Goal:** Determine whether the Windows Agility SDK package is compatible with the particular Proton/vkd3d-proton path COGBox ships against.

Microsoft Agility SDK uses `D3D12SDKVersion` and `D3D12SDKPath` exported by the executable to tell the D3D12 loader to load the app-local `D3D12Core.dll`; Microsoft describes the version/path handshake and matching requirements in its [Agility SDK setup guide](https://devblogs.microsoft.com/directx/gettingstarted-dx12agility/). vkd3d-proton's current documentation says its intended Windows-facing deployment is `d3d12.dll` plus `d3d12core.dll` as native Win32 DLLs and its changelog says the D3D12Core split used by Agility-style layouts is supported. That is encouraging, but it does **not** establish how this project's exact SDK 1.614 app-local Microsoft binary is resolved through Steam Deck's Proton build. [vkd3d-proton README](https://github.com/HansKristian-Work/vkd3d-proton#using-vkd3d-proton), [vkd3d-proton changelog](https://github.com/HansKristian-Work/vkd3d-proton/blob/master/CHANGELOG.md).

Run a controlled build matrix on the same Deck, Proton version, game files, save, settings and shader cache:

| Build | Agility SDK exports and app-local `D3D12Core.dll` | Purpose |
|---|---|---|
| A: current release | Present, SDK 614 | Establish whether current package reaches D3D12 device creation. |
| B: Proton-runtime experiment | No app-local Agility core; use a build/runtime arrangement that allows Proton's vkd3d-proton D3D12Core to service the calls | Isolate the app-local SDK loader from vkd3d-proton. Do not distribute this build until validated on Windows too. |
| C: loader-compatible experiment | Keep the exports but verify which exact `d3d12.dll` and `d3d12core.dll` modules Proton loads and where from | Check whether DLL override/module search behavior explains the difference. |

For every run, capture `PROTON_LOG=1`, `VKD3D_DEBUG=info`, the Proton version and the loaded module path. If testing Steam Linux Runtime behavior as well, Valve documents combining `STEAM_LINUX_RUNTIME_LOG=1` with `PROTON_LOG=1` to preserve the container/runtime log. [Valve Proton logging options](https://github.com/ValveSoftware/Proton#runtime-config-options), [Steam Runtime bug-reporting guide](https://github.com/ValveSoftware/steam-runtime/blob/master/doc/reporting-steamlinuxruntime-bugs.md).

Do not simply remove Agility from the Windows release: local code says Shader Model 6.6 is required, and the Windows runtime compatibility reason for bundling it is real. Prefer either a proven shared runtime path or a separately validated Proton build/package mode. Do not ship vkd3d-proton DLLs as a permanent app-local workaround without checking the interaction with the Steam-managed Proton version, DLL precedence, update behavior, and license obligations.

**Pass condition:** Logs identify the D3D12 implementation actually loaded, its reported SDK/runtime and shader model, and the same build reaches a menu on Deck and a baseline Windows PC. A working option becomes the release path; otherwise keep it clearly experimental.

### Priority 2 — make capability checks match vkd3d-proton on Steam Deck

**Goal:** Identify whether COGBox requires a D3D12 capability that vkd3d-proton/RADV does not provide or reports differently.

vkd3d-proton documents Vulkan 1.3, descriptor indexing and several Vulkan features/extensions as required; it recommends RADV for AMD and says it receives the most AMD testing. These are compatibility-layer requirements, not an assurance that every D3D12 feature query has the same result as a native Windows driver. [vkd3d-proton driver requirements](https://github.com/HansKristian-Work/vkd3d-proton#drivers).

1. Log each COGBox `CheckFeatureSupport` query, returned `HRESULT`, returned tier/value, and whether the capability is required or optional. At minimum cover Shader Model 6.6, `D3D12_OPTIONS` stencil-reference support, `D3D12_OPTIONS2` programmable sample positions, resource binding/heap tiers, typed UAV format support, rasterizer-ordered views and any feature that selects a different path.
2. Audit every use of a failed optional query. It must select a correct fallback, not leave an uninitialized tier/boolean or later call an unsupported interface. Keep truly required capabilities as a clear startup diagnostic.
3. Test Xenos programmable sample positions independently from the base renderer. If unavailable or wrong on the Deck vkd3d/RADV pair, keep that specific enhancement disabled for this path while retaining correct standard sample positions; do not disable all D3D12 rendering.
4. Capture feature-query results on Windows NVIDIA, Windows AMD, Steam Deck RDNA2/RADV and one SteamOS desktop AMD system. Compare them in a table before lowering requirements or adding workarounds.

**Pass condition:** The renderer either uses the required feature correctly or emits a specific supported fallback reason and continues. No false-positive claim of an active feature.

### Priority 3 — validate swap chain and Gamescope frame pacing

**Goal:** Make presentation smooth and predictable in Game Mode, Desktop Mode and docked use.

The game path runs through Wine/Proton and the SteamOS compositor (Gamescope), not a Windows-exclusive display mode. COGBox already suppresses exclusive fullscreen under Wine, which is an appropriate starting policy. The patched presenter requests a DXGI frame-latency waitable object, maximum frame latency 1, and optional tearing. vkd3d-proton also documents a runtime `VKD3D_SWAPCHAIN_PRESENT_MODE` diagnostic override, but that variable is for controlled testing; do not make undocumented overrides the product default. [vkd3d-proton environment variables and swap-chain mode](https://github.com/HansKristian-Work/vkd3d-proton#environment-variables).

Test the same repeatable scene and input route at:

- Steam Deck Game Mode, handheld at the panel's common refresh/cap combinations (30, 40/45, 60 and the panel maximum where available).
- Deck Desktop Mode in a window and borderless fullscreen.
- Docked Steam Deck at 1080p and 4K output, including monitor refresh changes and suspend/resume.
- A SteamOS desktop AMD system and Windows control system.

Measure presented frame-time distribution (median, p95, p99, worst hitch), guest frame time, CPU/GPU utilization, frame-limit adherence, power draw and whether the game is GPU-bound. Use Gamescope/MangoHud or the Steam overlay as a second measurement, but keep COGBox's guest-frame counter distinct from actual present cadence. A generated/duplicated guest frame and a displayed compositor frame are different quantities.

Test one variable at a time: current DXGI present path, VSync, frame-latency waitable object, tearing flag and `VKD3D_SWAPCHAIN_PRESENT_MODE` options if relevant. Do not enable exclusive fullscreen on Proton as a performance fix. If the waitable object fails or blocks too long, implement a robust fallback with a log rather than spinning, deadlocking or silently queuing many frames.

**Pass condition:** No periodic hitching, missed caps, deadlock or broken focus/restore in an hour of play; stable frame pacing at the target refresh in both modes; correct return from sleep and display-mode changes.

### Priority 4 — make FSR/DLSS temporal inputs correct before tuning presets

**Goal:** Make temporal upscaling stable on moving Gears content, preserve a sharp full-resolution HUD, and accurately report when an upscaler is truly active. Treat this as a D3D12 feature gate after the D3D12 device, presentation path and base game loop are stable. FSR and DLSS in the current renderer are D3D12 integrations; the current launcher selects COGBox Vulkan under Wine/Proton, so they are not presently an available SteamOS feature through that default route.

**The screenshot's main recommendation is already implemented in COGBox.** In `Gears2-Native/src/layer0_xenos/renderer/shadow_renderer.cpp`, the upscaler is injected at the scene-color resolve. Its output then feeds the game's later post-processing and HUD; after the resolve, the renderer switches the remaining frame to output scale. This is the right high-level separation to avoid upscaling the HUD and menu glyphs. The important nuance is that the current input is scene color before the later post-processing chain, rather than a fully post-processed 3D image. Keep this placement as the baseline, but verify every title, cutscene, menu and alternate resolve path. The screenshot is useful confirmation of composition order, not evidence that COGBox's temporal inputs or every post-process scale are correct.

**The highest-confidence local quality gap is still per-pixel dynamic-object motion.** `builtin_shaders.h`'s `kMotionVectorsCs` reads depth and reprojects pixels with the prior camera transform, and `shadow_renderer.cpp` dispatches that field as `FrameInputs::motion`. The current renderer also samples likely object-to-world constants and compares object samples to infer camera translation; that is useful camera estimation, but it is not a per-object/per-pixel velocity buffer and does not encode skeletal animation. A character or weapon moving with a stationary camera can therefore still have missing individual motion, causing temporal trails, ghosting or unstable detail. Verify the current matrix-sampling path by debug captures; do not mistake its camera-motion estimate for full object motion. The interface comment in `upscaler.h` says game velocity is layered on top “where it has one,” so either implement/confirm that path or make the comment accurately describe the current inputs.

There is a concrete Gears 2 lead in `notes/64-graphics-options.md`: it records a half-resolution velocity target from a game pass that draws moving/skinned meshes, encoded around 0.5 and clamped, and suggests decoding it over camera reprojection. That note is research evidence, not proof that the pass mapping is fully validated or reusable as-is. Verify its format, sign, scale, jitter convention, coverage and timing against captured frames. Gears 3 and Judgment need their own title-specific validation even though they share the renderer.

**FSR is also dispatched without reactive/transparency masks.** In `fsr_upscaler.cpp`, the dispatch fills color, depth, motion, output, jitter and sizing, but leaves `reactive` and `transparencyAndComposition` unset. AMD describes these masks as optional inputs but recommends masks for transparencies and other content that does not behave like opaque geometry; omission can increase ghosting or reconstruction artifacts around particles, smoke, muzzle flashes, animated emissive details and rapidly changing composition. [AMD FSR Super Resolution input guidance](https://gpuopen.com/manuals/fsr_sdk/techniques/super-resolution-upscaler/). DLSS also depends on good motion/depth inputs for temporal reconstruction; NVIDIA's programming guide emphasizes supplying the correct per-frame inputs and motion-vector scale. [NVIDIA Streamline DLSS programming guide](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideDLSS.md).

**Recommended implementation sequence:**

1. **Preserve and audit composition.** Keep the scene-color → upscaler → post-processing → HUD/menu → present order. Trace all three title builds and alternate paths (loading, cutscenes, pause/menu, split-screen if supported). Capture the scene, upscaler output, final post-process, and final UI separately to prove HUD pixels are not temporally reconstructed and every downstream pass uses output dimensions correctly. This is especially relevant to reports that post-processing options do not scale properly at high resolutions.
2. **Add dynamic motion vectors.** Retain depth-based camera reprojection for static geometry, then merge valid per-object/per-pixel motion for moving geometry. Start by validating the Gears 2 native velocity pass identified in the notes; prefer a decoded native velocity buffer when its coverage is adequate, and otherwise emit motion from current/previous object and bone transforms. Define one explicit convention (current pixel to previous-frame position, render-resolution pixel units, y-down, correct jitter handling) and convert each title's encoding into it. Add a validity/coverage mask so absent vectors on particles, alpha-tested geometry and disocclusions are handled intentionally instead of looking like zero motion.
3. **Supply FSR masks where they improve reconstruction.** Build reactive masks from material/blend metadata and particle or emissive passes; build transparency-and-composition masks only where the content and SDK version support them. Keep opaque geometry low-reactive, and tune masks with frame captures rather than painting the whole scene reactive. Record when a mask is unsupported or omitted. Consult the exact bundled FSR SDK/API version before wiring fields because the mask contract differs across SDK generations.
4. **Validate temporal lifecycle and jitter.** Confirm the jitter applied to the 3D projection is the same jitter sent to the SDK, with documented sign and pixel units; keep the HUD and non-camera full-screen passes unjittered. Reset history on scene/camera cuts, load transitions, resolution/scale changes, device loss/recreation and failed evaluations. Check that the existing reset conditions cover these events and do not reuse stale history after toggling a mode. Compare motion-vector/depth/jitter debug views to native-resolution captures.
5. **Make render scale and UI truthful.** The current launcher maps quality to a 2/3 scene scale and ultra to 1/3 only at a 3x output ratio; performance uses 1/2 at 2x or 4x at 2x scene-to-output ratio as configured in the renderer. At 1x, FSR/DLSS behaves as native-resolution temporal AA rather than a render-resolution FPS boost. Expose requested mode, actual active provider, input/output dimensions and fallback reason. Consider fractional/arbitrary scale ratios only after the current integer-scale render-target transitions and post-process dimensions are verified.
6. **Separate Super Resolution from frame generation.** Do not describe DLSS/FSR Super Resolution as frame generation. COGBox already has an AMD FidelityFX frame-generation swap-chain path in `frame_generation.cpp` (patches 0146/0147), so the work is to validate and complete that implementation, not start from zero. Frame generation has separate inputs, pacing, UI/HUD treatment, latency and platform requirements; it must not be used to mask a broken limiter or unstable base frame pacing.
7. **Gate SteamOS claims on the actual backend and runtime.** First make forced D3D12 through Proton work and log the actual D3D12 implementation. Then validate FSR runtime loading and DLSS capability/runtime behavior under the exact Proton, vkd3d-proton, Mesa/RADV and Steam Deck combination. Current Wine behavior selects COGBox Vulkan and the current upscalers are D3D12 wrappers; do not label them available on SteamOS until that path is demonstrated. Do not infer that COGBox's own Vulkan backend supports these D3D12 integrations.

#### Deep-dive findings: what is implemented, what is still suspect, and how to isolate it

**The current status is “SDK paths execute in bounded scenes,” not “DLSS/FSR quality is validated.”** Local notes record 1,196/1,196 successful DLSS and FSR evaluations during a short Gears 2 ch02 walk, but that run predates the later camera-motion reconstruction. It was native-resolution AA, and “clean at a glance” is not a temporal quality test. It establishes that the wrappers could initialize and dispatch in that particular Windows/D3D12 build and scene; it does not validate upscaling ratios, full playthroughs, other titles, masks, current SDK/runtime versions, Proton, or the final presented image.

**Most likely cause of the visible temporal artifacts: incomplete motion, not a broken DLSS/FSR DLL.** The renderer's `kMotionVectorsCs` reprojects depth with the camera transforms and adds an inferred camera translation from object-constant votes. In the reviewed path, this is not the game's per-pixel velocity field merged into the generated buffer, and it cannot recover per-bone skinned motion or all independently moving objects. NVIDIA's current DLSS-G guidance describes dense vectors including camera and dynamic-object motion; AMD's FSR manual likewise recommends vectors for all opaque, alpha-tested and alpha-blended objects. Missing character/weapon motion predicts the wrong prior-frame sample and appears as ghost trails, smearing, unstable thin edges or a character “dragging” during camera motion. [NVIDIA Streamline DLSS-G input requirements](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideDLSS_G.md), [AMD FSR input and motion-vector guidance](https://gpuopen.com/manuals/fsr_sdk/techniques/super-resolution-upscaler/).

**FSR's absent masks are a verified quality gap, with a low-risk first improvement.** `fsr_upscaler.cpp` leaves `ffxDispatchDescUpscale::reactive` and `transparencyAndComposition` at their zero-initialized defaults. AMD says a missing reactive mask becomes an internally generated cleared 1×1 mask; it specifically recommends alpha-derived reactivity for blended content and recommends limiting reactive values to about 0.9. The transparency/composition mask serves a distinct history-lock role for effects such as animated textures and special composition. Therefore, do not treat the two masks as interchangeable or blindly set either to 1: first add an opaque-vs-blended scene-color capture or material/blend classification, generate alpha-informed reactive coverage for particles/smoke/muzzle flashes, and create transparency/composition coverage only for surfaces/effects that need reduced history lock. If no usable material metadata exists at the resolve point, AMD's luminance-based helper needs both opaque-only and opaque-plus-blended color inputs; confirm COGBox can capture both before choosing that approach. Test with the exact bundled FSR API version and log whether each mask was supplied. [AMD FSR 3.1.6 reactive and transparency/composition mask guidance](https://gpuopen.com/manuals/fsr_sdk/techniques/super-resolution-upscaler/).

**Jitter and vector conventions need an image-level proof, not just matching comments.** COGBox documents vectors as current pixel to previous-frame position, render-resolution pixels, y-down, with the projection jitter removed from vectors; its wrappers pass that motion scale as 1 and pass jitter separately. These are plausible SDK conventions, but a sign inversion or an inconsistent late-jitter/depth path can still make the images shimmer or trail while every dispatch returns success. Add debug views for raw game vectors, camera-only reprojection, merged vectors, invalid/disoccluded pixels, and the actual projection jitter; then check a static scene under a pure camera pan (static geometry should have coherent screen motion), a stationary camera with a moving character (only that character's vectors should move), and a scene cut (history reset). Verify motion does not contain camera jitter twice and that the same jittered depth/color frame is paired at the resolve. AMD's current manual states jitter must be applied to the scene and passed in render-pixel units; its older temporal API explicitly discusses the correct current-to-previous convention, so keep the selected SDK's contract pinned to the version COGBox actually builds. [AMD FSR 3.1.6 jitter/motion documentation](https://gpuopen.com/manuals/fsr_sdk/techniques/super-resolution-upscaler/), [AMD FSR 2.3.4 motion-vector contract](https://gpuopen.com/manuals/fsr_sdk/techniques/super-resolution-temporal/).

**Scene placement is broadly correct for HUD stability, but it trades reconstruction quality against later effects.** COGBox upscales the lit scene at its resolve, then runs later post-processing and UI at output scale. This prevents the HUD from being fed into the temporal upscaler and follows AMD's guidance that tone mapping, bloom, depth of field and motion blur are commonly better after SR. However, the input is before some effects; the post chain must preserve the same visual response and be correctly scaled. COGBox-specific reports that post-processing does not scale at higher resolutions therefore need their own tests: compare each effect's radius, kernel footprint, depth sampling and motion inputs at 720p/1080p/1440p/4K, not merely the final upscaler sharpness. Film grain/noise applied before reconstruction can be amplified; keep it after SR if the game pipeline permits. Do not move the upscaler later as a blanket fix, because that could reintroduce HUD/glyph wobble or feed already tone-mapped color to the temporal algorithm. [AMD FSR post-processing placement guidance](https://gpuopen.com/manuals/fsr_sdk/techniques/super-resolution-upscaler/).

**HDR and exposure are plausible sources of brightness/pumping differences.** Both local wrappers enable SDK auto-exposure for HDR because they do not receive the game's exposure texture. In the DLSS wrapper, `InPreExposure` is populated but HDR also sets `AutoExposure`; the FSR wrapper sends `preExposure` and enables auto-exposure. AMD says exposure needs to match subsequent tone mapping and that poor exposure selection can materially reduce quality. Compare the final tone-mapped image across SDR/HDR and bright-to-dark transitions, logging input color range, pre-exposure, exposure path and output luminance. If the game's exposure can be extracted, pass the correct exposure data; otherwise retain auto exposure only after confirming it does not fight UE3's own exposure/tone-map response. Don't misdiagnose this as a generic “FSR is washed out” or DLSS color bug without the same scene rendered through the native path.

**Resolution modes and marketing names need to reflect actual ratios.** The render targets are based on integer multiples of 720p, so the available render/output pair may not match a vendor preset's conventional scale at every display resolution. For each resolution, display and log the exact input and output dimensions, per-axis scale, provider/mode, and whether the mode is native-AA, upscaling, or supersampling. A preset label such as “Quality” is not enough to identify what the SDK is actually doing; avoid selecting a named vendor preset solely from the horizontal ratio when the vertical ratio differs, especially ultrawide. The existing ultrawide minimum-height workaround (512 pixels) should be tested for all aspect ratios and providers, with a clear “unsupported dimensions / native fallback” status rather than a silent mode switch.

**Treat SDKs and providers as different products and versions.** The local notes identify FSR 3.1.5 at the time of the historical sweep; AMD's current SDK documentation now lists FSR 3.1.6, FSR 4.1.2 ML upscaling, FSR 3.1.6 frame generation and separate frame-generation swap-chain versions. A newer loader/provider may choose a different algorithm by GPU, and support on RDNA 4 is not equivalent to support on Steam Deck RDNA 2 or on NVIDIA. Record the provider version COGBox already queries and pair it with the shipped loader/provider DLL hashes and GPU. Test FSR 3.1.x and FSR 4 as distinct provider cases; do not assume a binary replacement preserves the API contract or image quality. [AMD SDK technique/version list](https://gpuopen.com/manuals/fsr_sdk/).

**DLSS Super Resolution does not require replacing NGX with Streamline.** COGBox's direct NGX `Init_with_ProjectID` / `CREATE_DLSS_EXT` / `EVALUATE_DLSS_EXT` path is a legitimate integration approach for DLSS SR; Streamline is relevant when integrating features through its plugin interface, especially DLSS Frame Generation and Reflex. Keep direct DLSS SR stable unless a measured interoperability or feature requirement warrants migration. If DLSS FG is ever evaluated, NVIDIA's current guide adds requirements beyond SR—including Streamline's Reflex integration and correctly synchronized frame markers—and explicitly lists Vulkan as unsupported for the documented D3D12 FG path. Do not infer that DLSS SR success proves DLSS FG support. [NVIDIA DLSS SDK repository/programming guide](https://github.com/NVIDIA/DLSS), [NVIDIA Streamline DLSS-G guide](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideDLSS_G.md).

**Per-title tuning is already encoded and must stay visible in regression coverage.** The Gears 3 and Judgment app headers set title-specific object-constant, camera-constant and scene-format defaults; Gears 3 also enables late jitter for a reported cutscene/depth interaction. Those are not generic renderer facts. Maintain separate per-game captures and logs for scene-color format, depth decoding, jittered draw coverage, late depth draws, camera transform, motion coverage and SDK result. A shared renderer test that only passes Gears 2 is not a pass for Gears 3 or Judgment.

**Recommended triage order for a reported “DLSS/FSR looks wrong” case:**

1. Capture exact game/title-update/build, GPU/driver, OS/runtime/backend, SDK/provider versions, requested and active mode, and input/output dimensions. Ensure the requested upscaler actually ran; on Proton, first prove the game used D3D12 rather than the launcher's current Wine-to-COGBox-Vulkan selection.
2. Compare native output and native-resolution temporal AA with the same camera and scene. Then enable one SR provider at native resolution (DLAA/FSR Native AA) to isolate temporal reconstruction from spatial scaling; then test one conservative ratio. Keep frame generation, HDR, third-party injectors and overlays off for this first comparison.
3. Save a short frame sequence plus captures of input color, depth, jitter, camera vectors, game/object vectors, merged vector field, masks, upscaler output, post-process output and final UI. A single screenshot cannot diagnose history artifacts.
4. Fix vector sign/scale/jitter/depth validity and reset behavior first; then add/tune FSR masks; then validate exposure and post-process scaling; only then tune DLSS model/presets, sharpening and render ratios.
5. Re-run the same scene on all three titles, GPU vendors and supported renderers. Track GPU/CPU cost, frame pacing and image artifacts separately; a quality improvement that costs more than it returns on the target Deck GPU should remain optional.

**Relevant peer-project evidence:** The Lost Odyssey recompilation's public changelog documents iterative fixes for FSR/DLSS/TAA temporal flicker in skies, caves, shadows and cutscenes, FSR/DLSS history resets during fades, stutters, and a case where FSR/DLSS working images were recreated every frame and reduced performance. This reinforces a targeted COGBox checklist: verify stable resource/context lifetime, no unintended per-frame re-creation, history reset semantics on fades/cuts, and image-based scene regressions. It is a useful independent recompilation analogue, not evidence that its code or fixes transfer directly. [Lost Odyssey Recomp changelog](https://github.com/freefrank/LostOdysseyRecomp/blob/main/CHANGELOG.md), [temporal-upscaling feasibility note](https://github.com/freefrank/LostOdysseyRecomp/blob/main/docs/notes/temporal-upscaling-feasibility.md).

#### Frame generation, OptiScaler, Lossless Scaling and low-latency options

**Current COGBox status:** `Gears2-Native/src/layer0_xenos/renderer/frame_generation.cpp` contains an AMD FSR frame-generation swap chain and one generated frame between game-rendered frames. Its source comments explicitly record two quality limitations: the game's HUD and COGBox overlays are included in interpolation, and characters' own movement is absent from the motion vectors. The renderer captures scene depth and camera-reprojection motion; object-constant sampling estimates camera translation, but does not provide complete per-pixel rigid or skinned-object motion. Treat this as a real prototype with known artifacts, not a finished player feature. Check shared-layer behavior, build flags and runtime fallback in Gears 2, Gears 3 and Judgment separately.

**Recommended order:**

1. Finish the native-resolution base frame-pacing/limiter and pass the temporal SR quality gate above. Measure rendered frames, simulation rate, present rate and generated frames separately. Require a stable, useful base rate before interpolation; frame generation cannot make CPU-bound simulation, input response or real render throughput faster.
2. Fix frame-generation inputs before offering it broadly: per-object and skinned motion where recoverable, correct depth/jitter/scene-cut resets, a HUD-less scene or explicit UI composition path, and robust transitions through menus, no-scene frames, resize and device recreation. NVIDIA's DLSS-G documentation identifies depth, motion vectors and UI composition as engine inputs, while AMD's FSR 3 documentation calls for explicit UI composition and describes reactive/transparency masks. [NVIDIA Streamline DLSS-G programming guide](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideDLSS_G.md), [AMD FSR 3 integration overview](https://gpuopen.com/fidelityfx-super-resolution-3/), [AMD FSR 3.1 frame interpolation manual](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/super-resolution-interpolation/).
3. For COGBox's AMD path, first exercise `--gow2_frame_generation=swapchain` with generation off and prove identical image, cap, resize, window/overlay focus, HDR and clean exit versus the ordinary swap chain. Then compare FSR generation on/off at 30/40/45/60 base FPS in matching scenes, including slow/fast camera movement. Make it opt-in and display base FPS separately from presented/generated FPS.
4. Add AMD Radeon Anti-Lag 2 or NVIDIA Reflex only where COGBox has a supported, correctly placed low-latency integration. Measure end-to-end input latency with FG off/on, not only an SDK status flag. Keep FG disabled if latency support is unavailable or the base rate is too low; test Steam Deck separately because its driver/runtime and compositor path differ.

**OptiScaler — COGBox-specific conclusion:** A maintainer-confirmed Reddit reply on a COGBox post reports that OptiScaler works with the project and that a COGBox update improved the experience. This is positive real-user evidence that at least one COGBox build/configuration exposes an input path OptiScaler can hook; the comment as provided does not identify game, build, renderer, OptiScaler version, GPU, selected input/output provider or whether “works” means Super Resolution or frame generation. I checked the current renderer against OptiScaler's documented interfaces, and found a direct integration match:

- COGBox's DLSS wrapper calls NVIDIA NGX directly (`NVSDK_NGX_D3D12_Init_with_ProjectID`, `NGX_D3D12_CREATE_DLSS_EXT`, `NGX_D3D12_EVALUATE_DLSS_EXT`) with COGBox scene color, depth, motion vectors and output. OptiScaler documents DLSS/NGX inputs and replacing a game's selected temporal upscaler with another backend. The COGBox CMake build includes the NGX implementation and stages `nvngx_dlss.dll` only when the DLSS SDK is present.
- COGBox's FSR wrapper loads `amd_fidelityfx_loader_dx12.dll` and invokes FidelityFX API `CreateContext`/`Dispatch` for the upscaler. The COGBox build stages the FidelityFX loader and upscaler DLLs when that SDK is present. OptiScaler's current configuration explicitly supports FidelityFX API inputs (`EnableFfxInputs` / `UseFfxInputs`) and its library path accepts the FidelityFX D3D12 loader. That is a closer match to COGBox's FSR path than a generic DLL-proxy guess.
- These wrappers supply the temporal data OptiScaler expects to route: render-resolution color, depth, motion vectors, jitter, reset state and output dimensions. That establishes a technically plausible hook point for SR. It does **not** mean every output algorithm or every FG mode will work equally well: COGBox's vector quality and HUD composition remain renderer-level quality limits.

**Do any source changes need to be made just to use OptiScaler?** No specific renderer change is indicated by this code review or by the successful user report. COGBox already calls APIs OptiScaler documents hooking. If OptiScaler is working in the reported configuration, changing COGBox to call an OptiScaler-specific API would add unnecessary coupling and could break the native FSR/DLSS paths. The immediate work should be a reproducible, documented compatibility profile. Source changes become justified only if captures/logs show a repeatable interface defect, such as missing input resources, incorrect provider selection, incorrect output dimensions or a swap-chain/pacing conflict.

**Use the existing renderer as the input, OptiScaler as the optional output selector:** select an enabled COGBox upscaler (`fsr`, `dlss` or `xess`) so the renderer actually creates the corresponding SDK calls and temporal inputs; then use OptiScaler's documented setup/overlay to select the replacement output provider. If COGBox's upscaler is `off`, there may be no temporal upscaler call for OptiScaler to intercept. Confirm OptiScaler's log says it hooked the intended NGX or FidelityFX input and reports the selected output provider—do not infer success solely from an overlay option being selectable. Follow the official setup guide for the current release and use only official OptiScaler sources; its project warns about fake download sites and unofficial manager apps. [OptiScaler README and installation guidance](https://github.com/optiscaler/OptiScaler), [OptiScaler configuration for FFX inputs and runtime paths](https://github.com/optiscaler/OptiScaler/blob/master/OptiScaler.ini), [OptiScaler features](https://github.com/optiscaler/OptiScaler/blob/master/Features.md).

**Frame generation needs a separate, stricter test:** COGBox's native AMD FSR FG path installs a FidelityFX frame-generation swap chain and callbacks. OptiScaler also offers several FG input/output routes, including experimental OptiFG. Do not enable COGBox's `--gow2_frame_generation=fsr` and an OptiScaler FG output simultaneously during the first tests; that risks two frame-generation owners, competing swap-chain hooks or double interpolation. First test OptiScaler SR alone. Then test its FG with COGBox's native FG off and one documented OptiScaler FG input/source at a time; if testing native COGBox FSR FG, keep OptiScaler FG output disabled. For OptiFG-from-upscaler, inspect HUDFix results carefully: COGBox currently composes its HUD/overlays in the scene stream passed to its native FG, and OptiScaler's HUD tracking is experimental and can itself cause artifacts/crashes. Test native FG pass-through separately before trying any replacement. OptiScaler's own INI documents these distinctions and potential HUDFix caveats. [OptiScaler frame-generation configuration](https://github.com/optiscaler/OptiScaler/blob/master/OptiScaler.ini).

**A/B validation plan:**

1. Record a clean COGBox build hash and baseline logs/screenshots for each of Gears 2, Gears 3 and Judgment. Test the exact build and game that produced the Reddit success first; ask the reporter for the missing version/provider details if available.
2. On Windows D3D12, compare (a) no injection/native output, (b) OptiScaler installed with its default routing, and (c) one deliberate replacement provider. Use the same save, scene, internal/output resolution and cap. Begin with SR only; test native resolution/AA and a true upscale ratio. Repeat a DLSS input and FidelityFX input separately when available.
3. Confirm the loader/proxy method, exact DLLs loaded, hook success, input API, output API, SDK/runtime versions and actual resolution in logs. Detect silent fallback to COGBox's native SDK or native AA; compare image output rather than trusting a status menu alone.
4. Check temporal artifacts (moving characters/weapons, camera pans, disocclusion, smoke, muzzle flashes, cutscenes, subtitles, HUD and menus), HDR/SDR, resize/fullscreen transitions, alt-tab, overlays, crashes and clean uninstall/rollback. Record CPU/GPU frame times and COGBox-rendered FPS separately from generated/presented FPS.
5. Treat FSR FG / OptiFG as distinct cases. Change one FG owner at a time, compare base-rate/latency/frame pacing, and keep FG off if it destabilizes presentation or obscures the limiter. Then repeat the passing configuration on SteamOS/Proton and CrossOver independently; Windows success does not establish compatibility with their translation layers.

**Known integration risks and upgrade candidates:** OptiScaler injects/hijacks graphics-library interfaces and changes providers, so conflicts with another `dxgi.dll`/overlay hook or the custom FSR swap chain are possible. AMD's FSR 3 integration guidance specifically cautions that software intercepting DXGI can cause frame-pacing issues and that some overlay hooks can conflict with FG. Keep Steam, RTSS, vendor overlays and ReShade/RenoDX off for the first diagnosis, then add each one back separately. Also check OptiScaler's GPL-3.0 license and each vendor SDK's redistribution terms before bundling anything; supporting it as a user-installed optional tool is simpler than making it part of COGBox's release. [AMD FSR 3 integration compatibility notes](https://gpuopen.com/download/AMD_FidelityFX_Super_Resolution_3-Overview_and_Integration.pdf), [OptiScaler license and repository](https://github.com/optiscaler/OptiScaler).

**If a COGBox update is warranted after testing:** prefer small, generic diagnostics/documentation over an OptiScaler dependency: log the actual COGBox SDK input/provider, render/output dimensions and fallback reason (existing status logging already covers much of this); add an optional “third-party upscaler hook” troubleshooting note; and document that exactly one FG provider must own the swap chain. Add a code compatibility shim only if a captured failing OptiScaler version demonstrates a specific FFX/NGX/DXGI interop mismatch and the fix also preserves the native path. Do not hard-code OptiScaler filenames, ship its proxy DLL, or auto-edit its INI based only on one success report.

**Lossless Scaling:** The Windows Steam utility's LSFG can interpolate older games without built-in FG, so it is the cheapest external experiment because it needs no COGBox renderer patch. It sees the final displayed image rather than COGBox depth, velocity, HUD-less color or simulation timing; expect possible HUD/edge artifacts, added GPU work and latency. It cannot validate or fix COGBox's limiter. Test borderless/windowed mode, a stable internal cap and sufficient GPU headroom; compare base-rendered FPS to displayed FPS. SteamOS is a distinct community route: `lsfg-vk` is a Linux/Vulkan layer and Decky plugins automate setup; neither is the official Windows Lossless Scaling app nor an endorsed COGBox integration. Since Proton translates COGBox D3D12 through vkd3d-proton to Vulkan, a controlled Deck experiment is technically plausible after D3D12 launch and pacing work, but layer order with Proton, Gamescope, MangoHud and COGBox's swap chain must be verified. Do not promise support or make it a dependency. [Lossless Scaling on Steam](https://store.steampowered.com/app/993090/Lossless_Scaling/), [lsfg-vk Linux project](https://github.com/PancakeTAS/lsfg-vk), [Decky LSFG-VK plugin](https://github.com/xXJSONDeruloXx/decky-lsfg-vk).

**RenoDX:** Evaluate RenoDX as a per-game ReShade add-on/HDR and shader-pipeline research tool, not a ray-tracing or general FG implementation. It can replace shaders, inject buffers and alter swap-chain/texture resources, potentially useful for learning HDR tone mapping and color controls, but those same hooks can conflict with COGBox's D3D12 renderer or FSR swap chain. A generic ReShade HDR filter cannot recover scene-linear color once the game has tone-mapped it. If evaluated, use a separate build; confirm which scene/UI resources it reads; compare calibrated SDR/HDR output; and test the normal and FSR swap chains independently. Long term, COGBox-native HDR output and tone mapping are more supportable than shipping an injector. [RenoDX toolset](https://github.com/clshortfuse/renodx).

**Comparable Xbox 360 recompilations:** Lost Odyssey Recomp is the strongest peer example found: its project documents Windows D3D12 DLSS/FSR/XeSS upscaling and frame generation, and its changelog records later fixes for frame-gen pacing, scene transitions, occlusion and provider availability. Its renderer and game differ, so use its implementation and regression history as a design reference, not code to transplant. Estacado (The Darkness, Xbox 360) demonstrates native D3D12 DLSS/DLAA, FSR and XeSS Super Resolution; its developer described frame generation as still in progress because HUD separation remained. That is direct evidence the HUD issue is real work in another recompilation too. ### Priority 8 — make player-side recompilation feel like the current COGBox install experience

**Goal:** Publish a small, convenient COGBox launcher package without distributing the prebuilt game-port executables. The player downloads COGBox, selects a game copy they already own, and COGBox runs the supported ReXGlue code-generation and native build steps on that player's computer, then installs and launches the result through the familiar COGBox interface.

**Important current-state distinction:** COGBox's release script says it excludes `.xex`, `.xexp`, `.iso` and disc folders, but it currently copies the already-built `gow2.exe`, `gow3.exe` and `gowj.exe` from five game build variants into the release zip (`cogbox/tools/package_cogbox.ps1:5-6,21-26,123-127`). This means the proposed change is not simply “stop shipping game data”: the current zip excludes the original disc/game data while shipping native port executables and their runtime DLLs. A player-side build design must replace those port binaries in the public package with a local build pipeline. Keep the existing distinction between the game's data (already user-supplied) and the recompiled native executables clear in release notes and the package audit.

ReXGlue's documented model is suitable in principle: `rexglue codegen` analyzes an Xbox 360 XEX and emits portable C++23, after which the generated project is compiled with a host C++ toolchain. That is multiple heavyweight technical stages, so simply publishing source and telling players to install CMake, Ninja, Python, LLVM/Clang and the required SDKs would make the experience substantially harder than today's download-and-launch flow. The launcher should orchestrate and validate those steps rather than expose them. [ReXGlue SDK](https://github.com/rexglue/rexglue-sdk), [Codegen Pipeline Overview](https://github.com/rexglue/rexglue-sdk/wiki/Codegen-Pipeline-Overview), [ReXApp generated-project configuration](https://github.com/rexglue/rexglue-sdk/wiki/ReXApp).

**Recommended player flow (target experience):**

1. Player downloads one small, signed/hashed COGBox bootstrap package from the project's normal release page and opens it. Keep setup portable if that remains the current product preference; otherwise provide a conventional installer with the same steps.
2. The existing “add/install game” flow remains the entry point. The player selects an ISO, supported package, or extracted game folder/XEX as appropriate. COGBox validates the selected title, region/build and supported base/title-update variant locally, without uploading game data.
3. Before changing files, COGBox performs a preflight: supported host OS/architecture, available disk space, writable cache/install locations, required downloads and network access, compiler availability, and known game-image signature/version. Explain any failure in launcher language and let the player correct it without losing the selected game path.
4. COGBox fetches pinned ReXGlue/codegen and compiler dependencies from trusted project or official upstream releases as needed, verifies published hashes/signatures, and installs them in an app-managed toolchain cache. Avoid requiring users to find and install a developer IDE or invoke a terminal. Provide an offline/pre-cached option only if its size and license obligations are acceptable.
5. A single visible **Build game** action runs extraction/validation, code generation, configuration, compilation and linking with per-stage progress, elapsed time, cancel/resume where safe, and a clear “what is happening” explanation. Build one selected title on demand; do not make a player compile all three before playing the first one.
6. On success, COGBox registers the locally generated executable in the same per-game card and settings screen used today. The player presses **Play** as before. Subsequent launches reuse the local build; rebuild only when the input game/XEX or title update, project manifest/codegen version, compiler ABI or explicitly incompatible build settings change.
7. On failure, retain safe intermediate outputs for retry, identify the failed stage and concise cause, offer a copyable diagnostic report, redact user names and private paths by default, and avoid presenting an incomplete executable as ready to launch.

**Build and cache design:**

- Keep the generated C++ project, object files, build tree and resulting game executable in user-local application data or the selected game installation, never in the source repository or release archive. Separate per-title, per-region and disc/TU variants. Prefer a stable, user-visible cache path and a COGBox “clear/rebuild generated port” action.
- Key each completed build to hashes/versions, not just filenames: source executable and supported TU patch, game/title identity and region, ReXGlue SDK and codegen manifest revision, COGBox integration revision, target architecture, compiler/toolchain version, and relevant build options. Do not rebuild just because the launcher updated if the generated port remains compatible; do rebuild when a build input or ABI actually changes.
- Maintain a project-owned manifest for every game variant describing accepted input forms, required files, title-update handling, expected outputs, toolchain versions, architecture and validation checks. Fail closed on unknown/mismatched game inputs rather than generating a binary from the wrong title or variant.
- Benchmark full code generation and compilation time, peak RAM, temporary/final disk footprint, and cold/warm rebuild behavior for all three games on minimum supported hardware. Preflight enough free space before starting. Show real progress by stage; do not invent a percentage if a tool only reports coarse output.
- Keep build logs local by default, redact account names and absolute paths in reports, and make all telemetry explicitly opt-in. Never upload an ISO, XEX, generated game C++, symbols or executable as part of diagnostics or an automatic build service.
- Audit upstream tool licenses and redistribution requirements before bundling any compiler/runtime. Prefer pinned official downloads plus cryptographic verification; do not download and execute an unverified “latest” artifact. Use a signed bootstrap/release where the project's signing pipeline supports it.

**Platform rollout and scope:** Start with the Windows x64 path, where the current launcher and ports are Windows programs and the release pipeline already targets Windows. Prove that a clean Windows machine with no developer tools installed can complete the first build entirely through COGBox. Then design separate, platform-specific build backends for SteamOS/Linux and macOS; their compiler host, output binary format, runtime and graphics path are not automatically solved by the Windows build flow. In particular, do not claim that CrossOver can transparently compile the current Windows port or that a Windows binary produced on Steam Deck is a native Linux build. Keep the UI and game-selection experience common while the platform toolchain steps are explicit and independently tested. This also preserves the D3D12-first order: first produce and validate the same Windows D3D12 executable locally, then use it in the Proton/CrossOver investigations above.

**Risks and decision gates:** Local generation/build will take longer on first run, consume substantial temporary disk space, and may be blocked by antivirus, permissions, missing network access or unsupported hardware. Measure these costs before promising “one click”; support cancel/retry and build-on-demand. ReXGlue documentation warns that codegen can reject inputs; do not routinely force past validation failures. A locally generated executable can still contain game-derived code, so player-side generation should not be described as a legal guarantee or as eliminating all rights/licensing questions. Review project licenses, upstream tool terms and the distribution model before release.

**Release validation gate:** Build the archive from a clean checkout and scan its complete contents and nested archives. Assert that it contains the launcher, public manifests/integration code and allowed generic dependencies, but contains no title-port executable, generated game C++/object files, game image, disc data, user logs, saves or caches. Test first install, retry after a failed download, cancel, resume, low disk space, paths with spaces/non-ASCII characters, antivirus quarantine, user without admin rights, no network, changed game/TU hash, launcher update, and all three titles. Compare a clean local result against the established developer build and verify launch, save/reload and renderer behavior before removing existing ready-to-run packages.

**Reference workflow:** The public Gears 3 Recomp build instructions illustrate the manual version of this pipeline: user-supplied game input, ReXGlue SDK, CMake and a native C++ compiler/toolchain. Gears3-Azura describes a more integrated user-facing model where the launcher builds from the player's dump. **Pass condition:** A non-developer can install COGBox, select a supported copy, wait through a clear first-build process, and play each supported title without manually installing an IDE or running command-line build steps. The release zip has no prebuilt title executables or generated game code; local builds are cached, reproducible enough to diagnose, validated against the selected game/TU, and never upload game-derived files.

**Goal:** Stop lights and other visibility-tested effects from rendering through walls, while keeping visible geometry from popping or disappearing and avoiding an unacceptable GPU/CPU stall.

The project's own test notes establish the tradeoff: jobs 139-141 found that immediately answering from delayed results caused visible objects to flicker, with results arriving about three frames later; leaving query answers off avoided that symptom but meant the guest kept its fake “visible” result and paid for extra draws. Confidence: **likely** for effects controlled by guest occlusion queries; it does not explain every light artifact.

**Upstream evidence argues against one global fix:** Xenia Canary and Edge's per-title tracking lists Gears of War 2 and 3 as benefiting from `strict` queries and says `fast` is better than `fake`; Judgment is also listed as `strict`, with some unoccluded clouds explicitly noted as unrelated to occlusion queries. Xenia Canary describes `fast` as returning cached results before the GPU catches up and `strict` as waiting for the actual answer, with a performance cost. Those semantics match the latency-versus-flicker tradeoff COGBox measured, but Xenia's implementation timing cannot be copied blindly into a statically recompiled game.

There is also a separate, game-side lens-flare avenue: the Xenia Canary patch set contains per-title “Disable Lens Flares” patches, and the Gears 2 patch discussion identifies the `LensFlare` setting in `GearGame\\Config\\Xbox360-GearEngine.ini` as a workaround for bright sources ignoring occluding geometry. Therefore first classify each report as (a) lens flare/sun flare, (b) an object or particle effect governed by a ZPD query, (c) an intentionally unoccluded screen-space effect, or (d) a depth/MSAA/resolve artifact. Turning off lens flares can be a user-facing fallback, but it is not a fix for broken general occlusion and changes the game's intended look.

**Recommended implementation sequence:**

1. **Instrument before changing semantics.** For each title, log query begin/end report addresses, query identity/generation, number of guest draws covered, whether every draw was actually submitted, host query segment count, submission fence, result-ready frame, consumed/returned guest value, and whether a later correction was too late. Keep normal logs aggregate and make per-query tracing opt-in; redact personal paths.
2. **Audit the query protocol independently for all three games.** Confirm guest begin/end report layout, marker/ready bits, end-minus-begin arithmetic, report reuse, query type, segment handling across command-list submissions, and the game's polling loop. Do not assume Gears 3's poll/yield hook applies unchanged to Gears 2 or Judgment. Do not write a guessed result as though it were final.
3. **Make readiness visible to guest code.** Preferred direction: keep the report in the guest's documented “pending” state until the correct fenced result is available, and ensure the game's query-poll path yields/retries instead of consuming a stale estimate. Gears 3 has a project-specific poll-yield patch noted in local code; verify whether the corresponding paths exist and are safe in Gears 2 and Judgment. Never block the renderer/command-processing worker waiting for a fence if that worker must submit the work that will satisfy the fence; that creates a self-deadlock. If a synchronous fallback is tested, wait only at a verified guest query-read boundary, use a bounded wait, and handle device removal/timeout explicitly.
4. **Preserve D3D12 slot and readback lifetime invariants.** Keep a query slot unavailable until the fence for its resolve has completed; do not read mapped readback data early; never recycle a query handle while a pending report can still refer to its previous generation. COGBox's current D3D12 backend already has slot-held/fence bookkeeping and returns “not ready” for incomplete results—retain these invariants while fixing the guest-facing timing.
5. **Keep incorrect hidden answers biased toward visible.** If a low-latency estimate is still required, unknown/stale results should conservatively say “visible.” A zero/hidden answer should require a current result for the same query identity, or a deliberately validated temporal rule. The existing “three trusted zeros” rule did not remove flicker when latency remained around three frames, so increasing the threshold alone is not sufficient.
6. **Keep host-only rendering out of guest query accounting.** Audit command-list splits and every renderer-owned draw/pass around guest query spans. Internal resolve, overlay, copy, and full-screen composition operations must neither accidentally add samples to a guest query nor corrupt its open/close pairing. The D3D12 backend currently segments queries across submissions; test this explicitly when ring pressure or an early submit occurs inside a guest query.
7. **Treat Vulkan honestly.** The current `vulkan_backend.cpp` implements the interface with `BeginOcclusionQuery() { return 0; }` and `GetOcclusionResult(...) { return false; }`. Thus COGBox's own Vulkan backend does not currently provide this host-query path. Keep Vulkan query answers disabled/clearly unavailable until its query pool, resolve/readback and guest readiness semantics are implemented and validated. This does not prevent D3D12 through Proton, where vkd3d-proton translates the D3D12 query implementation.
8. **Offer a reversible workaround.** If exact results cannot yet meet the deadline, expose an explicitly labeled per-game “Disable lens flares” or “Compatibility: conservative visibility” option where supported, and retain the current visible-biased behavior as the safe default. Make clear that disabling flares trades an effect for hiding the symptom; do not label it a renderer occlusion fix.

**Focused test matrix:** Use one repeatable scene per game with a bright light/effect moving behind a thin wall, a thick wall, and an edge; include an open-sky control, moving camera, occluder animation, checkpoint reload, and a long static run. Capture image sequences so one-frame pops are visible. For each run record CPU/GPU frame time, query latency distribution, unresolved/dropped queries, wrong-hidden answers, too-late corrections, draws per frame, and actual displayed frames. Compare: answers off/fake-visible, current delayed-answer path, strict/wait-at-consumer experiment, and any per-title LensFlare-off workaround. Run on Windows D3D12 first, then the same build through forced D3D12 on Steam Deck/Proton; repeat on NVIDIA and AMD, since the available upstream tracking is mainly NVIDIA-tested and explicitly asks for AMD feedback.

**Pass condition:** Each title has a documented baseline and zero reproducible “visible object disappears” events in the test scenes; occlusion-dependent lights/effects respect occluders; no unbounded wait/deadlock; no query result is consumed before its fence; and the measured cost of accurate results is acceptable. If the game intentionally renders a specific flare unoccluded, record that as a game-side behavior and offer the optional flare setting separately.

### Priority 10 — optimize CPU/GPU frame time using measured bottlenecks

**Goal:** Deliver stable, well-paced frame rates across Windows D3D12, SteamOS/Proton D3D12, and macOS/CrossOver D3D12, without sacrificing correct game timing or image quality. COGBox already has substantial optimization work and CPU/GPU timing infrastructure; the next gains should come from current, repeatable, per-title and per-platform traces rather than broad optimization guesses.

**Recommended frame-rate targets:**

- **Primary target: stable 60 FPS** on capable Windows hardware and as the aspirational Steam Deck/CrossOver target. The frame interval budget is 16.67 ms. Treat the 60 cap as a delivered-present goal, not merely a launcher selection or game-thread counter reading.
- For a 60-FPS release claim, aim for at least 95% of steady-state presented-frame intervals at or below 16.67 ms, with p99 below 25 ms and no recurring >33.3 ms hitches after shader and pipeline warm-up. Also record the game critical-thread time and GPU active time; each needs headroom. If one misses this target, state the actual stable cap and hardware/settings instead of describing the build as “60 FPS.”
- **Fallback targets:** use a stable 30 FPS mode when title timing or device limits require it; use 40/45 FPS on a Steam Deck display/refresh configuration that supports the matching cadence. Validate presentation cadence and frame pacing for each refresh/cap pair.
- **Do not make 120 FPS the cross-title default.** Keep higher caps experimental and title-specific until simulation, animation, audio, input polling, camera, split-screen, cutscenes and networking have been verified at that rate. A recompiled Xbox 360 game can render faster while its internal clock remains slower or otherwise mismatched; other recompilation projects have documented and fixed exactly this class of clock-rate desync. [SVR07-Recomp timing/60-FPS notes](https://github.com/thecapibara/SVR07-Recomp-Linux).

**Local COGBox evidence and implications:**

- `Gears2-Native/notes/52-speed-plan.md` and `notes/60-cpu-plan.md` contain useful historical Gears 2 Windows/RTX 3080 Ti profiles. At 1x, a 720p gameplay scene was CPU-limited by the recompiled game's render thread and renderer CPU work, while the GPU took about 4.3 ms; the guest render thread was near saturation. A guest PPC/codegen optimization improved measured uncapped time about 4–5% in two scenes, while some renderer-only changes could not improve the cap until the bottleneck moved. This is a direct warning against treating every low FPS report as a GPU problem.
- The same notes show the bottleneck changes with resolution: a Gears 2 ch10 run at 3x/4K was GPU-limited at roughly 20.7 ms (about 48 FPS), with most time in shading/draws and smaller texture-load/resolve costs. In an earlier 2x run, a diagnostic texture-cache miss walk inflated CPU time; disabling that diagnostic changed the scene from about 46 to 79 FPS. Do not treat diagnostic-mode or old-note numbers as current release performance; reproduce them with the current build and settings first.
- Another Gears 2 result attributed about 77% of a 720p scene's measured GPU time to EDRAM transfers. That is a strong example of why D3D12 optimizations should be ranked by measured pass-level time rather than shader intuition. The renderer already records GPU timestamps by category and has CPU-side subsystem profiling; use these first and turn on more expensive per-draw diagnostics only for short captures.
- These measurements are primarily Gears 2 and older build snapshots. They do not prove Gears 3, Judgment, Steam Deck or CrossOver share the same bottleneck. Generate independent profiles for each title/backend/device combination.

**Optimization workflow:**

1. **Separate the clocks and counters.** Report guest/game FPS, COGBox completed guest frames, COGBox actual `Present` calls, compositor/displayed cadence, and generated frames as separate values. The game's own FPS counter, COGBox overlay, NVIDIA/RTSS/Steam overlay, and a frame-generation overlay may measure different stages. With frame generation disabled, timestamp the real present path and compare it against external present telemetry; if frame generation is enabled later, expose both base and generated/presented rates. A 60 setting plus a 180 overlay reading is a measurement-semantic investigation until actual present cadence shows the cap is exceeded.
2. **Build a reproducible benchmark path.** Use the same executable/title update, save, chapter/scene, camera, input script, output resolution, render scale, cap, VSync and cache state. Warm shader/pipeline caches separately from cold-start testing. Run at least three steady-state captures of 60–120 seconds after loading; exclude startup, loading, shader warm-up, screenshot/checkpoint tools and background compilation from steady-state averages, while reporting their hitch costs separately. Preserve frame-time CSVs and short video/image sequences.
3. **Measure three timelines together.** Record presented-frame intervals, per-thread CPU time/ready/wait time, and GPU timestamps for whole-frame and expensive renderer categories. Add GPU queue/fence waits, command-list submission gaps, pipeline/descriptor/texture-cache misses, allocation/upload time, memory pressure, clock/thermal state, and dropped or repeated presents. Avoid adding per-draw timestamps to normal runs if the instrumentation changes performance; bracket whole passes first, then take targeted deep captures.
4. **Classify before changing code.** If lowering internal render scale materially improves frame time, investigate GPU-bound work (shader cost, render-target/EDRAM transfers, resolves, texture traffic, overdraw, synchronization). If it barely helps, inspect the critical game/recompiled thread, renderer recording/submission, lock contention, guest query polling and CPU-side state/descriptor/texture lookup. If neither CPU nor GPU work explains the gap, inspect limiter waits, VSync, present queues, compositor cadence, CPU scheduling, I/O and periodic maintenance.
5. **Optimize CPU-bound work in measured order.** Profile the recompiled game thread separately from renderer threads. Check whether remaining cost is genuine guest scene/visibility logic or host overhead (per-draw pipeline/state decoding, repeated constants/bindings, memory copies, texture keys/lookups, locks and guest query spin loops). Prefer reuse/caching of unchanged state, lower allocation/copy counts, event-driven waits instead of busy loops, and parallel preparation only where ordering and backend thread-safety allow it. COGBox's own historical Gears 2 tests show both codegen register-local optimization and CPU wait changes can help, but the optimal result differs between capped/uncapped scenes; rerun correctness captures and per-title sweeps after each default change.
6. **Optimize GPU-bound work by category.** Use the D3D12 timestamp breakdown and PIX/Nsight/Radeon GPU Profiler where supported to find the expensive pass, then reduce redundant transfers/resolves, overdraw, expensive shader work or render scale only when captures prove it. Test 720p, 1080p, 1440p and 4K separately; resolution scaling is a diagnostic, not an excuse to lower the default before image-quality tradeoffs are reviewed. Keep the scene/HUD scale and post-processing correctness checks from Priority 6 in the loop.
7. **Treat first-visit stutter as a separate metric.** Measure cold and warm shader/pipeline startup, then gameplay frame time. COGBox's notes report shader-pack warm-up improvements and async pipeline work, but cold driver pipeline creation can still hitch. Do not hide a multi-second first-use stall inside a good average FPS result. For first-run chapter smoothness, evaluate the user-requested distributable per-chapter shader cache described below; do not substitute a full-game launch precompile or long startup hold. Preserve a warm local cache and record invalidation/version behavior.
8. **Preserve intended game timing.** Compare the selected FPS limit with guest simulation delta, animation and input responsiveness. COGBox has per-game cap plumbing and some title-specific behavior (including a Gears 3 cap adjustment); independently verify each title's actual limit at 30/40/45/60 and supported high-rate modes. Keep simulation/vblank timing independent from host Present pacing where the runtime permits it. Add explicit regression checks for audio cadence, cutscenes, split-screen and online/LAN timing before exposing >60.
9. **Keep platform captures distinct.** On Windows D3D12, use PIX timing/GPU captures and vendor profilers. On SteamOS, pair COGBox timestamps with MangoHud/Gamescope or Steam present telemetry and vkd3d-proton traces; do not compare CPU/GPU timing definitions without documenting them. On CrossOver, record actual D3DMetal selection and use host-level Metal telemetry where it works with the translation layer, alongside COGBox present and CPU/GPU logs. Apple’s Metal System Trace/GPU tools can profile Metal workloads, but a trace of a translated application is not automatically an event-by-event COGBox D3D12 profile. [PIX timing and GPU capture overview](https://devblogs.microsoft.com/pix/introduction/), [NVIDIA Nsight Graphics](https://developer.nvidia.com/nsight-graphics), [AMD Radeon GPU Profiler](https://gpuopen.com/rgp/), [Apple Metal performance tools](https://developer.apple.com/documentation/xcode/metal-developer-workflows).

**What similar recompilation projects teach:**

- The [Need for Speed: Most Wanted NX renderer study](https://github.com/StevensND/nfsmw-nx/blob/main/docs/native-renderer.md) used counterfactual runs with GPU work removed to distinguish CPU from GPU limits; in its tested race, removing GPU work did not materially raise FPS, exposing CPU-side GPU emulation/command processing as the limiter. Its Nintendo Switch-specific figures do not transfer to COGBox, but the diagnostic method does: change one subsystem at a time and measure its effect.
- The [WWE SmackDown vs. Raw 2011 ReXGlue port](https://github.com/shaneomac1337/SVR2011-Recomp) documents a roughly 10 ms music-player wait that constrained some scenes and a separate exact 60 Hz vblank/frame-pacing fix; it also used asynchronous pipeline creation to avoid a hitch on first encounter. This illustrates that an apparent GPU/FPS problem may be a title-specific CPU wait or pacing mismatch.
- The [SVR07 Recomp notes](https://github.com/thecapibara/SVR07-Recomp-Linux) explicitly report rendering above 100 FPS while the internal simulation clock ran at half speed, then a fix that restored 1:1 timing at 60. This supports keeping unlocked FPS behind per-title timing validation.
- ReXGlue-based projects use distinct renderers/backends and platform targets. Their README-reported peak FPS is not an apples-to-apples COGBox benchmark. Borrow their measurement questions and timing fixes, not their numeric performance claims or code without license review.

**Useful tools and sources:** Microsoft's [D3D12 timestamp guidance](https://learn.microsoft.com/en-us/windows/win32/direct3d12/timing) describes GPU timestamp queries and CPU/GPU clock calibration. [PIX](https://devblogs.microsoft.com/pix/timing-captures/) can correlate CPU threads and GPU queues; NVIDIA's [Nsight Graphics](https://developer.nvidia.com/nsight-graphics) and AMD's [Radeon GPU Profiler](https://gpuopen.com/rgp/) expose API-level and hardware-level bottlenecks on supported configurations. Apple's [Metal workflow tools](https://developer.apple.com/documentation/xcode/metal-developer-workflows) provide Metal timelines for the native Metal path and whatever translated activity CrossOver exposes.

**Pass condition:** For each game and supported platform, the report states actual present cadence, base/game cadence, frame-time percentiles, cap/VSync behavior, cold/warm cache behavior and CPU/GPU bottleneck. The 60-FPS mode sustains its defined frame-time gate in representative gameplay on its declared hardware/settings, with no simulation-speed regression; lower stable caps are documented for devices that miss it. No optimization lands as a default without a repeatable speedup, image/gameplay equivalence check, and regression coverage for all three titles.

### Priority 16 — test the Jacinto Gears 3 HD texture pack against COGBox's separate Xbox 360 game data and renderer

**Goal:** Determine whether the community HD texture pack made for Project Jacinto can be adapted safely to COGBox's Gears 3 recompilation. Treat this as an experimental, per-title asset-compatibility investigation; do not install the pack into a player's live game or claim compatibility based on its working in Jacinto.

**What the pack actually targets:** The current Nexus Mods page describes the pack as compatible with **Jacinto v1.1.1**, and its installation guide copies phased files into that PC game folder and runs package-injection scripts. Its changelog describes direct in-place injection into cooked Unreal `.upk` packages, reconstructed texture payload tables, full mip-chain repairs, package compaction, and a `HD_TexturePack_Phase<N>.version` marker used by Jacinto's Multi Patch Tool to raise only selected texture group limits. The same page documents older-version incompatibilities and crash cases, including missing top mips/texture-size-cap combinations. The pack is therefore more than a folder of interchangeable loose images. [Jacinto HD Texture Pack and changelog](https://www.nexusmods.com/gearsofwar3/mods/28), [Jacinto Multi Patch Tool compatibility notes](https://www.nexusmods.com/gearsofwar3/mods/27).

**Relevant COGBox difference:** COGBox's shared renderer consumes guest Xenos texture fetches and reconstructs their host textures, including Xenos untile/layout, packed mip tails, endian conversion and format conversion (`Gears2-Native/src/layer0_xenos/include/xenos/renderer/texture_cache.h:1-6`). The Jacinto pack, by contrast, is packaged for a particular PC build and changes cooked UPK files plus game-specific texture streaming configuration. COGBox uses the Xbox 360 Gears 3 XEX/data and a statically recompiled runtime; neither the pack's compatibility marker nor Jacinto's INI edits automatically affect COGBox. It is unknown whether its injected packages can be consumed correctly by COGBox's Xbox 360 asset path, and whether the higher mip data and group caps map to the renderer's actual resource requests.

**Investigation sequence:**

1. **Pin the exact artifact and provenance.** Record pack version, phase, archive hash, Jacinto build it targets, installer/tool versions, Nexus author notes and license/redistribution terms. Download only from the author's official Nexus page. Do not put pack archives or modified game packages in COGBox's repository or release.
2. **Audit the injector before executing it.** In a disposable VM or isolated copy, inspect every script and tool for target path resolution, backup/restore, package-format assumptions, hard-coded Jacinto checks, marker writes, configuration changes and network behavior. Confirm the installer cannot escape the chosen game root or overwrite unrelated files. The pack's page records that previous injector versions could corrupt package property blocks, mishandle mipmaps, and crash on particular campaign content, so a clean backup and version pin are required.
3. **Compare package compatibility offline.** Use a legally obtained Gears 3 Xbox 360 data set and a separate Jacinto v1.1.1 PC data set. Compare package IDs/names, Unreal package versions, platform flags, endian/compression, export/import tables, texture payload layout, mip offsets, formats and cooked-top-mip behavior. Determine whether the pack's replacement UPKs are actually valid for the Xbox 360 game files before attempting to launch them. Do not copy entire Jacinto packages into COGBox based on matching filenames alone.
4. **Build a reversible one-package prototype.** Only after the format audit passes, use a disposable COGBox Gears 3 disc/TU6 install and one non-critical package/texture group. Keep originals, hashes and a rollback script. Check game package loading, texture identity, all mip levels, BC formats/alpha, anisotropic views, streaming transitions, texture cache invalidation and whether the texture is requested from the expected guest memory/package path.
5. **Expand by phase and content risk.** Test character/weapon/vehicle textures before environment/world phases, which touch more assets and can increase memory use substantially. Exercise the prologue, transparent objects, LUT/color grading, maps with known affected packages, Act 4 Episode 6 (the Nexus page documents a prior crash there), and long streaming/level transitions. Check for missing textures, wrong material channels/colors, shimmering, black/white surfaces, crashes and out-of-memory behavior.
6. **Map the streaming controls instead of copying PC settings.** Identify which COGBox guest texture requests and renderer caps correspond to the Jacinto Multi Patch Tool's `MaxLODSize`, `LODBias`, mip-filter and texture-pool changes. Apply only a COGBox-specific bounded option if the game's package data really contains those mips and resource budgets permit it. Never blindly import Jacinto INI edits or marker files; do not raise all texture limits based on the pack marker alone.
7. **Measure the cost and test platforms.** Compare original versus pack per scene: texture bytes, working set/VRAM use, uploads, cache hits/misses, streaming stalls, GPU/CPU frame times and visual output. Start on a desktop Windows D3D12 build; then test Steam Deck/Proton using the same pack and scene. Test CrossOver only if the underlying Gears 3 PC/Xbox recomp path itself is supported there. Provide an easy per-phase disable/restore path and make low-memory behavior fall back safely.
8. **Keep a strict separation of outcomes.** Record “works in Jacinto PC,” “package parses in COGBox,” and “renders correctly in COGBox D3D12” as separate states. A success on one does not prove the next. Do not generalize Gears 3 texture replacements to Gears 2 or Judgment; each title needs its own asset compatibility evidence.

**Pass condition:** A pinned pack phase can be applied to a disposable player-owned Gears 3 data copy, reliably rolled back, and shown to load and render the intended high-resolution mip levels correctly through COGBox D3D12 without package corruption, visual regressions, unacceptable stutter or memory failures. If package compatibility fails, document that the pack remains Jacinto-only and use the research to guide a separate COGBox-native texture pack/import format.

### Priority 17 — research a small DXR proof of concept only after lighting and D3D12 stability

**Current finding:** A targeted scan of `Gears2-Native/src/layer0_xenos/renderer` for DXR interfaces, acceleration structures and ray-tracing API symbols found no implementation. COGBox currently translates the Xenos graphics workload through its raster renderer; a DXR-capable adapter alone would not add ray-traced effects. Microsoft's D3D12 ray-tracing API requires explicit resource/geometry setup, acceleration-structure build/update, ray-tracing pipeline/state objects and dispatch. COGBox would also need a meaningful geometry/material representation that survives guest draw translation, including alpha-tested materials, animated characters, destructible or changing geometry, and scene/lifetime synchronization. [Microsoft Direct3D 12 ray-tracing documentation](https://learn.microsoft.com/en-us/windows/win32/direct3d12/direct3d-12-raytracing), [Microsoft DXR functional specification](https://microsoft.github.io/DirectX-Specs/d3d/Raytracing.html).

**Recommendation:** Do not promise “ray tracing” as a near-term feature and do not begin with path tracing or ray-traced global illumination. First fix existing correctness issues in occlusion queries, shadows, light visibility, depth and motion vectors. Then assess lower-cost raster/screen-space options (contact shadows, SSAO, screen-space reflections) with explicit quality/performance budgets. If those gates pass and a captured scene provides stable mesh/material data, prototype one optional DXR effect—prefer a limited shadow or reflection test—behind adapter capability checks and a raster fallback. Compare image quality and frame time on Windows GPUs, Steam Deck/RADV through Proton, and CrossOver/D3DMetal independently. Deck hardware/runtime capability and frame cost must be measured; do not infer support from desktop D3D12 or from the existence of DXR support in vkd3d-proton. The latter can expose DXR functionality through Vulkan extensions on supported stacks, but it does not supply COGBox's missing scene data or renderer integration. [vkd3d-proton project](https://github.com/HansKristian-Work/vkd3d-proton).

**Evaluation gates:**

1. Prove which guest meshes, transforms, materials, alpha tests and dynamic updates are available at the right point in COGBox's renderer. Build a resource inventory and estimate BLAS/TLAS memory/build cost before selecting an effect.
2. Query D3D12 ray-tracing tier and device/driver support at runtime; keep DXR optional. On Proton, log vkd3d-proton, Vulkan extension and RADV versions; on CrossOver, query D3DMetal behavior rather than assuming Windows DXR APIs map through it.
3. Prototype one effect in one repeatable scene; provide an immediate raster fallback. Test smoke/particles, alpha-tested foliage, cutscenes, animated enemies, camera cuts, device loss, resolution changes, memory pressure and all three titles.
4. Record GPU/CPU frame time, acceleration-structure memory and build/update time, image differences, stutter and artifact rate. Reject the feature if it reduces the stable target frame rate or requires broad fragile hooks.

**RenoDX relationship:** RenoDX can help investigate per-game HDR/shader behavior through ReShade add-ons, but it does not create DXR geometry, acceleration structures or ray-traced lighting. Treat its output as a reference and compatibility experiment, not as the implementation of ray tracing. COGBox-native HDR controls and any future DXR effect should be integrated into the renderer's own frame graph and output path.

**Pass condition:** A scoped effect works on all advertised target builds, uses the correct dynamic scene data, has a measured fallback and provides a documented quality/performance benefit. Otherwise retain accurate raster lighting and leave DXR as deferred research.

## Research findings and source notes

1. **D3D12 on Linux is a supported architecture in Proton, not native Windows D3D12 execution.** vkd3d-proton describes itself as implementing D3D12 on top of Vulkan and the D3D12 implementation used by Proton. Its intended Win32 DLL deployment works in Wine/Proton. This validates the broad approach, not COGBox's compatibility with every feature. [vkd3d-proton README](https://github.com/HansKristian-Work/vkd3d-proton#vkd3d-proton)
2. **AMD RADV is the right first SteamOS target.** The vkd3d-proton project says RADV is its recommended AMD driver and its most-tested AMD driver, while requiring a modern Vulkan feature set. Use Steam Deck as the primary real-device gate and a desktop RADV system as a useful diagnostic control; avoid extrapolating from NVIDIA Windows results. [vkd3d-proton driver requirements](https://github.com/HansKristian-Work/vkd3d-proton#drivers)
3. **Agility support is plausible but must be proven for COGBox's exact deployment.** Microsoft requires the SDK version and relative app-local path exports. Current vkd3d-proton documents `d3d12core.dll` split support, but COGBox packages Microsoft's own app-local 1.614 core. Confirm actual module resolution on Steam Deck; old reports demonstrate that D3D12Core/Agility loader behavior has caused Proton startup failures, but don't establish the current result. [Microsoft Agility SDK setup](https://devblogs.microsoft.com/directx/gettingstarted-dx12agility/), [vkd3d-proton changelog](https://github.com/HansKristian-Work/vkd3d-proton/blob/master/CHANGELOG.md), [historical vkd3d-proton Agility issue](https://github.com/HansKristian-Work/vkd3d-proton/issues/1456)
4. **Do not use DXVK as the D3D12 fix.** DXVK is principally the D3D9/10/11 translation layer; vkd3d-proton is the D3D12 layer. They share DXGI infrastructure, which is why the COGBox D3D12 present path still needs attention. [vkd3d-proton README](https://github.com/HansKristian-Work/vkd3d-proton#using-vkd3d-proton)
5. **Steam's own tools are sufficient to debug the Windows binary on Deck.** Valve documents debugging Windows binaries running through Proton on Steam Deck, as well as Proton and Steam Linux Runtime log collection. That provides an established workflow before considering a Linux-native build. [Steamworks Steam Deck debugging](https://partner.steamgames.com/doc/steamhardware/debugging), [Proton logs](https://github.com/ValveSoftware/Proton#runtime-config-options), [Steam Runtime logs](https://github.com/ValveSoftware/steam-runtime/blob/master/doc/reporting-steamlinuxruntime-bugs.md)
6. **A Linux-native recompilation is a later, separate project.** A Linux host executable would remove Wine's Windows API layer, but it would require the runtime, launcher, file/input/audio paths and build system to support native Linux. It would not automatically improve the current Windows D3D12 path. First exhaust the lower-cost Windows-port-through-Proton route and quantify any hard blockers.
7. **There is a directly relevant native Mac comparison project.** Gears3-Azura reports a native Apple Silicon/macOS build of the Xbox 360 Gears 3 recompilation using ReXGlue and a Metal backend. This proves a native Mac path is being pursued for the same game/runtime ecosystem, not that COGBox's Windows executable works through CrossOver. Its platform architecture and public design notes are useful comparative evidence; its restrictive project license means code reuse requires explicit permission. [Gears3-Azura README](https://github.com/Carolux97/Gears3-Azura)

## Shader authorship, cache provenance and first-visit hitch reduction

### What COGBox writes itself

COGBox does write substantial renderer shader code. The clearest example is [`Gears2-Native/src/layer0_xenos/renderer/builtin_shaders.h`](C:/COGBox/Gears2-Native/src/layer0_xenos/renderer/builtin_shaders.h): it embeds fixed HLSL for rectangle-list geometry, depth/colour resolves, present/gamma conversion, texture and memory copies, and sharpening. Its header says the fixed shaders are game-free, the project-authored parts are MIT, and identifies the portions following Xenia Canary as BSD-3-Clause with notices in `THIRD_PARTY_NOTICES.md`. The shader sources are compiled at runtime; they are not game shader binaries.

The renderer also writes its own translation/compiler machinery. `hlsl.cpp` turns Xenos shader instructions into generated HLSL and labels the translator implementation MIT, while documenting that its semantics follow Xenia/rexglue's BSD-licensed interpreter/translator. `dxbc_gen.cpp` directly emits host DXBC for supported instructions, and `dxbc_spirv.cpp` translates that generated DXBC to SPIR-V. These are original implementation components, with upstream-derived behavior appropriately identified; the shader *programs they generate* still originate in game-provided microcode.

There are third-party shader assets too. The embedded SMAA HLSL/tables are copied from the SMAA project and carry its MIT notice. Some built-in geometry/depth/shader math follows Xenia Canary under BSD-3-Clause, and the sharpening source identifies its relationship to AMD FidelityFX RCAS. Any distributed built-in shader source or compiled form needs the applicable project and third-party notices preserved. This is a provenance summary from repository headers, not legal advice.

### What is game-derived and currently local

[`Gears2-Native/src/layer0_xenos/include/xenos/renderer/shader_cache.h`](C:/COGBox/Gears2-Native/src/layer0_xenos/include/xenos/renderer/shader_cache.h) explicitly describes the cache as “guest shader microcode -> our translated HLSL -> host bytecode” and says the on-disk default is `out\shader-cache`, “never committed: game-derived.” It also describes recorded `.ucode` microcode as game-derived and never committed. At runtime, `shader_cache.cpp` writes compiled DXIL/SPIR-V (or other host shader bytecode depending on backend) into the per-run cache; on a compile failure it writes the generated game-derived `.failed.hlsl` for diagnosis. The renderer's default `gow2_renderer_shader_record` is enabled, and the guest microcode is recorded under `ucode` to support later warm-up.

The D3D12 pipeline library and Vulkan `VkPipelineCache` are also generated locally from the pipelines/shader modules encountered on that machine. They are driver/backend-specific artifacts, not portable shader source. Even if their exact contents do not look like a standalone shader file, they were created from game-derived guest shaders; do not place them in the public release until provenance, portability and redistribution have been reviewed. The conservative distribution boundary is: package COGBox-authored renderer shaders and required licensed components/notices; let each player create guest-shader and pipeline caches from their own game files.

### Existing local cache/prebuild mechanisms (context only; not the preferred direction)

The project already has two relevant mechanisms, but neither currently provides a ready-made distributable chapter shader pack:

- `ShaderCache::WarmFromDisk()` re-translates previously recorded local `.ucode` or `recorded.pack` records and queues missing compiled bytecode in the background. This helps a returning player after the shaders have been seen once; it cannot supply shaders for a first-ever visit unless they are obtained from that player's own game packages.
- `Gears2-Native/src/layer2_ue3/shader_prebuild.cpp` scans packages the game itself opens, extracts local pixel-shader microcode and asks the renderer/driver to prebuild it while a level loads. Its code comments explicitly say this uses the player's own game files and writes nothing to disk. The option is currently off by default. The comment records why: one cold-area test offered about 10,000 shaders, most were not needed in time, and doing the work doubled that chapter's frame time. It also records that roughly 70% of drawn pixel shaders were present in package data and that XDK-patched vertex shaders generally did not match package microcode. Therefore “prebuild everything during loading” is not a safe solution and is not complete coverage.

The user's preferred direction is a distributable per-chapter opening shader cache, described in the following proposal. The local-only alternatives below are contingencies if legal review or portability testing rules out a shipped game-derived cache; they are not the preferred user experience.

1. Keep all source game files and extracted microcode local to the user's install. Do not make a community-generated `.ucode`, `.dxil`, `.spv`, `.failed.hlsl`, `shaders.pack`, or pipeline-cache bundle from someone's game files part of a release artifact.
2. During the player's first local build/launch, use their installed game packages to discover shader microcode for selected likely-upcoming content. Precompile only shaders that are actually referenced by the first playable seconds, and rate-limit the work to a defined CPU/GPU budget while a loading screen is already visible.
3. Prefer low-cost translation and creation of shader stages to full pipeline creation only when the pipeline's complete render-target/depth/sample state is known. Otherwise warm the complete pipeline list using actual pipelines recorded from that user's prior play.
4. Prioritize the next chapter/loading transition and recently observed shaders; stop or yield prewarm work immediately when live rendering needs CPU/GPU resources. Track shader coverage and first-use misses so the packer can measure whether the warm-up helps.
5. Reuse locally recorded shaders and per-device pipelines across runs, keyed by title/update, renderer/API, compiler/translator version, and GPU/driver identity. Invalidate incompatible entries safely and retain a fallback that compiles on demand.
6. Evaluate chapter-specific first-run compilation with a replayable, game-data-local harness. Require lower first-30-second hitch time with no doubled load-frame time, no missed shaders/black draws, and consistent results across the three games before enabling it by default.
7. If the desire is to distribute a small prebuilt starter pack, limit it to shaders demonstrably authored by COGBox (fixed renderer shaders) or non-game-derived metadata. Do not include guest shader bytecode extracted from a Gears installation without an explicit legal review/authorization.

**Bottom line:** COGBox writes fixed renderer shaders that can be considered for distribution with required notices. The shaders translated from Gears microcode and caches/pipelines built from them are a separate, game-derived category; the current project design generates them locally. The user prefers a small bundled per-chapter opening cache over a prewarm that adds launch delay. The broad package prebuild experiment is not an acceptable substitute without explicit reconsideration because it made a cold chapter substantially slower.

**Files checked:** `builtin_shaders.h`, `hlsl.cpp`, `dxbc_gen.cpp`, `dxbc_spirv.cpp`, `shader_cache.h/.cpp`, `shader_prebuild.cpp`, `shadow_renderer.cpp`, `vulkan_backend.cpp`, `Gears2-Native/LICENSE` and `THIRD_PARTY_NOTICES.md`.

## Proposed distribution feature: ship a per-chapter opening shader cache

**User goal:** Include enough prebuilt shader data with the COGBox release to make approximately the first 10–30 seconds of every chapter run very smoothly on a player's first launch. The intent is not to precompile the entire game at startup or make every user wait through a full-game warm-up; the cache should cover the most visible early gameplay in each chapter.

### Technical feasibility and constraints to resolve

- COGBox already translates guest Xenos shader microcode from each player's game data and saves guest microcode plus compiled shader bytecode in its local shader cache. A representative cache is not automatically universal: chapter paths, title updates, graphics API, renderer/shader backend, compiler version, resolution/settings, GPU driver, and device can change which shader **stages** or complete **pipelines** are used or whether the stored compiled objects are usable.
- A 10–30-second capture per chapter may miss assets triggered by a different route, checkpoint, cutscene skip, combat encounter, enemy composition, or player settings. It may reduce common-case stutter but cannot be described as a complete no-stutter guarantee without coverage data.
- The cache must be distinguished from a shader manifest. A manifest might contain hashes or identifiers describing shaders to prepare, while the cache contains guest microcode or compiled output. Neither should be assumed legally safe to distribute without review; the actual game-derived microcode and translated/compiled shader bytecode are the higher-risk artifacts.
- Current project code labels recorded guest shader data and translated/compiled cache data as game-derived and keeps it out of commits. The existing chapter package prebuild reads from the player's own game files, but its broad test caused substantial load-time cost and is disabled by default. Those existing mechanisms do not establish that a captured public release cache is authorized, portable, or a good fit.

### Research and prototype plan

1. **Inventory the exact candidate files.** For each proposed artifact, record whether it is COGBox-authored fixed renderer shader source/bytecode, guest shader microcode, generated HLSL, DXIL/DXBC/SPIR-V, a D3D12 pipeline library, a Vulkan driver pipeline cache, or a manifest. Record its source, game/title-update dependency, build step and current cache location.
2. **Get a rights review before public distribution.** Ask qualified counsel or the relevant rights holder/maintainer to review redistribution of each game-derived artifact and of any manifest generated from game code/data. The user's local recompile does not itself answer whether COGBox may distribute a captured derivative cache.
3. **Measure representative coverage.** For each game and chapter, use clean user-owned game data, a defined title update, and a recorded route covering the first 10, 15 and 30 seconds after gameplay begins. Record shader hashes and pipeline descriptions, compile hitches, missed shaders, and remaining cache misses. Include first run, restart, checkpoint reload, and alternate route/cutscene skip.
4. **Test portability separately.** Test whether a shader-stage cache survives compiler/backend changes and whether pipeline cache data is valid across vendor, GPU, driver, API, renderer and settings variants. Treat a driver cache as device-specific unless experiments and API guarantees prove broader reuse. Never silently consume incompatible blobs; reject and rebuild safely.
5. **Keep game variants explicit.** Validate the pack against each supported title update and game. Do not merge data across Gears 2, Gears 3 and Judgment just because they use a shared renderer. Ensure the COGBox launcher selects only the matching game/version/backend cache.
6. **Measure release and startup trade-offs.** Track pack size per game and total release size, cache lookup/read time, first-boot time, and frame-time percentiles for the opening gameplay. Require a demonstrated reduction in first-run shader hitches without shifting the same cost into a long launch delay or growing the download unreasonably.
7. **Define fallback behavior.** Missing or mismatched cache entries should compile locally through the existing path. Give a clear progress/loading state if a required shader is not ready; do not show a black or hung window. Keep locally generated results in a per-user writable cache rather than modifying the distributed install.
8. **Make a distribution decision only after the legal and technical gates.** If game-derived cache redistribution is approved and portability/coverage are adequate, package a versioned per-title pack with provenance, hashes, compatibility metadata, and a safe invalidation path. If review rejects distribution or tests show the pack cannot be portable, document that blocker and return with the available options; do not silently replace the requested bundled-cache feature with a long local prewarm, which the user has rejected.

**Acceptance target:** On a clean first launch, for all three titles, the representative first 10–30 seconds of each chapter show a measured reduction in shader-compilation stalls compared with an empty local cache; common route variations do not produce major regressions; launch time and package size stay within a documented budget; cache mismatch/rebuild works; and distribution has passed rights review.

### Important correction: a shader cache alone may not eliminate pipeline hitches

The local `shaders.pack` is a cache of compiled guest shader stages (the shader cache source writes bytecode records there). It is separate from the D3D12 pipeline library (`pipelines-d3d12.bin`) and the Vulkan driver's `VkPipelineCache`. A stage cache hit can avoid translating/compiling that guest shader again, while the renderer may still have to create a graphics/compute pipeline for a particular combination of shaders, render-target/depth formats, sample state, and other pipeline state. A missing PSO can still cause a first-use stall. Therefore the chapter-cache proposal must state exactly whether it ships shader-stage bytecode, pipeline state data, or both, and measure each source of hitch independently.

D3D12 serialized pipeline state data is explicitly hardware-, driver-, and machine-specific; Microsoft documents errors for blobs from another adapter or old driver. Vulkan's cache header identifies implementation vendor, device, and cache UUID, and the driver is responsible for accepting compatible cache data. These are strong portability limits for a release-wide cache. [Microsoft D3D12 cached PSO documentation](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_cached_pipeline_state), [D3D12 pipeline-library compatibility](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device1-createpipelinelibrary), [Vulkan pipeline cache header](https://docs.vulkan.org/refpages/latest/refpages/source/VkPipelineCacheHeaderVersionOne.html).

**Required added test:** For each representative first-30-second route, record separate cache hits/misses and time for (a) guest-microcode decode/translation, (b) host shader-module creation, and (c) full PSO/pipeline creation. Run an empty-cache baseline, a shader-stage-only cache, and—only if technically/legal approved—a matching pipeline-cache variant. Test mismatched vendor/device/driver/backend blobs and confirm the runtime safely discards them and recompiles. Do not claim “smooth first run” from shader-stage hit rate alone.

**Design implication:** A single public pipeline-cache blob cannot be assumed to serve Windows GPUs, SteamOS RADV, and CrossOver/MoltenVK/D3DMetal. The per-chapter feature may need to focus on shader-stage artifacts that are meaningfully reusable, with the remaining PSO work handled by the engine, or use a set of validated platform/device-specific pipeline packs. Measure the package-size and maintenance cost before committing to the latter.

**Current status:** This is a requested feature and investigation item, not a confirmed implementation or legal conclusion. The project has local shader/pipeline caching and experimental package prebuild code, but no evidence yet that it has a validated, legally reviewed, portable, chapter-complete shader pack suitable for public distribution.

### Optional launcher action: build or refresh a personal shader cache

**User-requested option:** In addition to investigating a bundled per-chapter cache, offer an optional launcher action for players who want to generate or refresh shader data themselves from their own installed game files. This is opt-in and player-initiated; it must not run as a compulsory full-game precompile on every launch or replace the preferred bundled-cache goal.

**Proposed player flow:** Add a per-game “Build / refresh shader cache” action in the launcher's game settings or maintenance tools. Explain that it may take time and disk space, show per-title/per-chapter progress where measurable, permit cancel/resume, and keep the normal Play action available. Offer scope choices only if the implementation can reliably enumerate them: current chapter/opening sections, selected chapters, or a full-game cache. Make the approximate duration and cache size estimate evidence-based rather than guessed.

**Implementation requirements:**

1. Read shader inputs only from the player's selected, validated game install; do not download, bundle, upload or include game data in reports. Keep outputs in the player's writable per-user cache, separate by game, title update, renderer/API, compiler version and GPU/driver where the artifact requires it.
2. Prefer collecting/compiling shader stages without booting the entire game only if the game package parser can enumerate the relevant shader microcode safely. If a valid pipeline requires live render-target/sample state that cannot be inferred from a package, say so and do not label the result a complete pipeline warm-up.
3. Reuse the existing cache format where compatible, but validate cache version and checksums, write atomically, preserve the previous working cache until the new cache passes validation, and recover from cancel/crash without corrupting a user's cache.
4. Do not promise zero stutter. Report coverage (shaders and pipelines prepared versus encountered on the next run), remaining misses, cache size, and elapsed time. This is important because COGBox's broad package prebuild experiment offered many shaders that were not used in time and doubled frame time in a cold-area test.
5. Make it clear that generated microcode and compiled guest shaders are game-derived local artifacts. The option does not grant permission to distribute/share caches; keep them out of release archives, support bundles and uploads unless the user explicitly chooses an appropriate diagnostic export and it is scrubbed/approved.
6. Add an explicit cancel button and do not run compilation on the renderer's critical frame thread. Schedule work with a bounded resource budget and monitor CPU/GPU responsiveness; the launcher can display progress while the game is not running.
7. Test the option on clean installs for all three games and supported title updates, verify cache reuse after restart, invalidation after a title/compiler/backend change, disk-full and permission errors, cancellation, and no adverse effect on normal launch.

**Priority relationship:** The requested bundled chapter-opening cache remains the main first-run smoothness goal, pending rights review and cross-device feasibility. The self-build action is a secondary opt-in path for users who want to generate or refresh their own local cache; it should not introduce mandatory startup delay.

## Roadmap addition — Bluetooth speaker/headset audio-video synchronization

**Goal:** Investigate and improve perceived audio/video sync when players use Bluetooth speakers or headsets. First determine whether the reported mismatch affects prerendered cutscenes, in-game sound effects/dialogue, or both; these paths need different fixes. Bluetooth output can add device/transport buffering that is outside the renderer's frame-pacing controls, so lowering the game's render latency alone is not a reliable fix.

### Project-specific starting point

A source search of the three games' native `src` trees and the Gears 2/3 `patches` found focus-mute handling through the SDK `audio_mute` cvar, but no COGBox-owned audio clock, audio-endpoint latency query, or audio/video synchronization layer in those paths. The game audio backend appears to be provided below these game-specific patches, so inspect the rexglue/SDK audio backend and the cutscene playback path before choosing an implementation point. Do not assume the D3D12 present timestamp is the audio playback clock.

### Recommended approach

1. **Instrument before tuning.** Record monotonic timestamps for decoded audio/video presentation, audio buffer submission/completion where available, and frame present. Compare wired output with multiple Bluetooth headsets/speakers and record sync error over several minutes, including after pause/resume, reconnect, and endpoint switching. Separate a constant offset from drift; the former suggests a fixed buffering delay, while growing error suggests clock-rate mismatch or timestamp handling.
2. **Use the audio device clock as the playback master for timestamped cutscenes.** Where the runtime exposes WASAPI, query `IAudioClock` position/frequency and `IAudioClient::GetStreamLatency` after stream initialization. Schedule cutscene frames against audio presentation time, dropping or repeating video frames when necessary rather than letting video run on an unrelated renderer clock. Windows Media Foundation documents this general model: a shared presentation clock synchronizes streams, and an audio renderer can provide the time source. If the SDK audio layer exposes only XAudio2, identify its supported timing/queued-buffer information and adapt the same master-clock design there.
3. **Treat reported stream latency as an estimate, not the complete Bluetooth delay.** `GetStreamLatency` reports the maximum latency for the initialized audio stream; it should not be assumed to include every Bluetooth codec, radio, headset DSP, or acoustic delay. Add an optional per-output sync calibration for the residual offset. Let the user delay video relative to audio in cutscenes; persist it per endpoint where possible, provide a reset, and avoid changing system-wide audio settings. If users report audio late in gameplay, explain that a cutscene sync offset cannot remove control-to-sound or simulation latency.
4. **Do not blindly shrink buffers or switch to exclusive mode.** WASAPI low-latency periods can help only when the endpoint and driver support them; Bluetooth transport may dominate. Very small buffers can cause underruns, and exclusive mode can silence other applications. Keep a stable shared-mode fallback and measure glitch rate as well as latency.
5. **Handle endpoint lifecycle and drift.** Reinitialize/re-query after Bluetooth disconnect/reconnect, default-device changes, sleep/resume, or audio stream invalidation. Use periodic audio-clock observations to detect drift and correct video scheduling gradually; avoid abrupt audio resampling or frame-time changes that create visible judder.
6. **Test and report by game and playback path.** Cover all three games, each cutscene implementation, dialogue and gameplay effects, wired and Bluetooth outputs, different sample rates, pause/resume, alt-tab, reconnect, and long playback. Include measured offset and drift in opt-in diagnostics without uploading headset identity or personal device names by default.

**Likely fix if the issue is cutscene-only:** Make the audio playback clock authoritative for cutscene frame presentation, then expose a small user calibration offset for Bluetooth output. **Likely fix if gameplay audio is also delayed:** First verify the audio backend's buffer queue and thread scheduling; a renderer-only change will not correct output-device latency. There is no universal software switch that removes Bluetooth's hardware/codec delay, so validate the measured improvement on real endpoints before promising a fix.

**Sources:** [Microsoft: Presentation Clock](https://learn.microsoft.com/en-us/windows/win32/medfound/presentation-clock) explains shared-clock synchronization and using an audio renderer as the time source; [Microsoft: IAudioClient::GetStreamLatency](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-getstreamlatency) documents the initialized stream's maximum latency; [Microsoft: IAudioClock](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nn-audioclient-iaudioclock) exposes device position and frequency; [Microsoft: Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio) describes supported buffer-period negotiation and its driver dependence.

## Roadmap addition — hide the pointer during controller navigation

**Goal:** When the launcher or COGBox in-game menu is being operated with an Xbox or PlayStation controller, hide the desktop mouse pointer so it does not remain over the game/menu. Restore it promptly when the player returns to mouse use.

### What the current source shows

The launcher already tracks input source in `Gears2-Native/cogbox/src/app.h` (`lastPad` and `padPs`). In `main.cpp`, controller button/axis events switch `lastPad` to controller, while key-down, mouse-button, and wheel events switch it back. The loop does not treat mouse-motion events as a switch back to mouse use. The launcher is built on SDL3 and Dear ImGui. The in-game menu separately polls controller input and feeds it to Dear ImGui navigation in `Gears2-Native/src/layer0_xenos/ingame_menu.cpp`. The source search found no explicit `SDL_HideCursor`/`SDL_ShowCursor` or `MouseDrawCursor` handling in the launcher or in-game menu. `page.cpp`'s `SetNavCursorVisible` controls the ImGui navigation highlight; it is not, by itself, the operating-system mouse pointer.

### Recommended behavior and implementation

1. Share a small “last active input” policy across the launcher and in-game menu: controller button/meaningful stick activity selects controller mode and hides the OS pointer; mouse movement/click/scroll or keyboard input selects pointer/keyboard mode and restores it. Require a meaningful stick dead zone and movement threshold so controller drift does not constantly switch modes.
2. For the SDL3 launcher, use SDL3's cursor visibility API (hide/show on the UI/main thread) or the SDL3 Dear ImGui backend's supported `ImGuiMouseCursor_None` path. Avoid calling cursor APIs from the controller polling thread. Update input-source tracking for actual mouse motion as well as clicks/wheel.
3. For the in-game overlay, implement the same policy through the game's window/input abstraction or its ImGui platform backend. Save the prior cursor state when opening the overlay and restore it on close, focus loss, game shutdown, or any initialization failure. Do not leave the pointer hidden after returning to the game or launcher.
4. Hide the pointer without warping it. Keep mouse input available so moving the mouse immediately restores the pointer and lets mouse users take control. Do not capture/confine the pointer unless a separate gameplay setting requires it.
5. Apply the behavior only while the relevant COGBox window/menu is active. Test windowed, borderless, fullscreen, alt-tab, launcher-to-game transition, Xbox and PlayStation controllers, reconnect/disconnect, stick drift, mouse movement while hidden, and shutdown/error paths. Confirm the cursor is restored in Windows and supported Wine/Proton sessions.

**Likely fix:** The launcher already knows when controller input becomes active, so hook that state to the platform cursor visibility API and add mouse-motion-based restoration. Add equivalent handling to the separate in-game menu path; hiding the launcher cursor alone will not hide the cursor shown over the game overlay. A short configurable idle timeout may be added as an optional refinement, but controller activity should hide the pointer immediately and mouse movement should bring it back without a long delay.

**Sources:** [SDL3 `SDL_ShowCursor`](https://wiki.libsdl.org/SDL3/SDL_ShowCursor) documents showing the OS cursor and that cursor visibility calls should run on the main thread; the [Dear ImGui SDL3 backend](https://github.com/ocornut/imgui/blob/master/backends/imgui_impl_sdl3.cpp) demonstrates the platform backend's hide/show behavior when a cursor is requested as `None`.

**Goal:** Confirm that campaign progress, checkpoints, settings, and other persistent game data are actually written and survive restart in all three native ports. Then determine whether player-owned saves created by Xenia Canary or Xenia Edge can be imported safely and reliably.

### Verification and implementation plan

1. **Prove persistence per title.** For each game and supported title update, start from a clean user profile, create a new campaign save/checkpoint, exit normally, relaunch, and confirm the game offers and loads the same progress. Repeat after a force close/reboot and after changing the selected profile. Test settings and any separate game-mode progress independently.
2. **Verify the storage contract.** Log the effective writable content/storage root, emulated user/profile/XUID, title ID, and content type at startup and when save APIs are called. Confirm the folder is writable, stable across launcher updates and working-directory changes, and outside temporary/extraction directories. Report disk-full, permission, corrupt-data, and missing-device errors instead of silently appearing to save.
3. **Protect user data.** Keep saves under a documented per-user directory, never inside replaceable game-install/extraction files. Use atomic writes or the runtime's safe save mechanism, and preserve/recover backups on interrupted writes. Add an opt-in backup/restore flow before any import or migration.
4. **Build a compatibility matrix.** Test each of the three games against Canary and Edge saves where the user owns the source save, recording emulator variant/build, title ID and region, title update, profile/XUID mapping, content path/layout, and save type. Use copies only; preserve the originals and compare checksums before/after. A transfer that appears in the menu but fails to load or later corrupts is not a pass.
5. **Add a safe import/export path only after evidence.** Prefer importing an entire validated save-content item through a file/folder picker and mapping it to the selected COGBox profile, rather than asking users to manually guess directory names. Validate title ID, profile association, expected structure, and destination containment; preview the target and make a backup before writing. Provide actionable errors for unsupported, mismatched, or encrypted/otherwise incompatible data.
6. **Test directionality separately.** Verify Canary → COGBox, Edge → COGBox, and (if supported and desired) COGBox → each emulator independently. Do not claim bidirectional interoperability from one successful import. Keep the user's original save untouched and explain that title-update, region, profile/XUID, or emulator-specific serialization differences may prevent transfer.

**Likely path if formats align:** Locate the emulator's user-owned Xbox 360 content save under its `content` store, preserve the full save item and relevant profile association, and import it into COGBox's matching title/profile storage through a validated importer. If the underlying save files are compatible but profile identity differs, add an explicit profile remap only if testing proves the save format permits it without invalidating checksums or metadata. If runtime storage APIs or serialization differ, implement conversion only with format-level evidence; never modify the source save in place.

**Acceptance criteria:** All three games can create, persist, reload, and back up saves after clean exit and restart; corruption and write failures are surfaced; and each Canary/Edge transfer direction is documented as supported, unsupported, or unverified with tested build/title-update/profile combinations. Until this matrix is complete, mark saving and save migration as **unverified**, not working or broken by assumption.

**Sources:** [Xenia Canary FAQ — saves and content folder](https://github.com/xenia-canary/xenia-canary/wiki/FAQ) notes the content location and that some profile-based game saves are broken; [Libretro documentation — Xenia Edge](https://docs.libretro.com/library/xenia_edge/) states Edge writes to emulated `content/` storage rather than RetroArch save files. These are storage/compatibility clues, not a guarantee that COGBox save data is compatible.

## PR #43 review — frame pacing and shader preparation

Reviewed the public [PR #43 diff](https://github.com/Shagg88/COGBox/pull/43/changes) at head `2055210f026371ad0d10e83d14234053de498803`. The change has plausible wins, especially avoiding a lost-wakeup in three game wait loops and persisting compiled D3D12 shader stages. It is **not a no-risk merge**, and the full-game startup gate should not be enabled by default without an explicit player choice and a way to cancel/fall back. The PR targets the Windows D3D12/DXBC path; its own description says Vulkan is unchanged, and the launcher marks the option unavailable under Wine. It therefore does not fix Issue #41's SteamOS/AMD/Vulkan rendering symptoms.

### Highest-priority adoption risks

1. **P1 — Whole-install shader preparation blocks first launch by default. Confidence: certain.** The launcher option is initialized enabled, sends startup-prebuild flags, and the guest thread is suspended until the scanner and all driver jobs report complete:

   ```cpp
   add(make("ShaderPrebuild", "Compile all shaders at launch", Tab::Graphics, Kind::Bool, SH, 1,
   ```

   ```cpp
   a.push_back("--ue3_shader_prebuild_startup=true");
   ```

   ```cpp
   while (!g_prebuild->ready.load(std::memory_order_acquire))
     std::this_thread::sleep_for(std::chrono::milliseconds(25));
   thread->Resume();
   ```

   The PR's own performance note reports Judgment first preparation at **12 minutes 45 seconds** and peak private memory of about **2.9 GB**; it reports much faster later cached starts. That is a substantial first-run/update delay for a setting presented as a normal graphics option. Keep the feature, but default it off or ask for opt-in before enabling the startup barrier, clearly state that the first run may take many minutes, and let the user launch with live compilation instead. The project owner also commented on the PR that players should not have to sit through 10+ minutes for a minor improvement.

2. **P1 — There is no timeout/cancel path for the startup suspension. Confidence: likely.** The detached resume thread waits only for `ready`; a stalled filesystem operation, stuck driver compile, or lost worker completion can keep the game thread suspended indefinitely. Add a bounded wait and cancellation/fallback state that always releases the guest thread, and make shutdown/device-loss paths publish completion. Verify the original SDK suspension count remains balanced across success, timeout, renderer failure, and app exit.

3. **P1 — This is D3D12-only, so it does not address the SteamOS/Vulkan issue. Confidence: certain.** The renderer enables prebuild only when its DXBC cache is active and Vulkan is not selected; the launcher also disables the option for Vulkan/Wine. Treat PR #43 as a Windows D3D12 optimization and evaluate SteamOS/Vulkan/AMD fixes separately. Do not use D3D12 test results as evidence that Issue #41 is resolved.

### Additional correctness, performance, and maintenance checks

4. **P2 — Background package reading can still compete with gameplay. Confidence: likely.** Startup preparation scans packages, but the file-open observer can queue packages opened later; `ReadPackage` then reads the entire candidate into memory and scans/decompresses it on the reader thread. The PR's own note says an earlier startup-disabled diagnostic saw CPU and texture-loading spikes while background package scanning was allowed. Lower the scanner's I/O/CPU priority, throttle it during active gameplay, and collect a frame-log A/B with background scanning on and off. Keep rendering/gameplay compilation work lower priority than live draws.

5. **P2 — A single package can be read into a very large allocation. Confidence: certain.** The implementation accepts candidate files up to 2 GiB and allocates a vector of the full size before scanning:

   ```cpp
   if (size <= 0 || size > (std::streamoff(1) << 31)) {
   ```

   ```cpp
   std::vector<uint8_t> data(static_cast<size_t>(size));
   ```

   This can create multi-gigabyte transient allocations, especially alongside decompressed package data and shader queues; the PR's 2.9 GB measured private-memory peak confirms that memory use is material. Prefer bounded streaming/mapping and impose a defensible per-file, total-memory, and decompressed-output budget; on exhaustion skip prebuild and continue with live fallback rather than failing game startup.

6. **P2 — Package paths are written verbatim to logs. Confidence: certain.** The new prebuild logs include absolute package/root paths:

   ```cpp
   REXLOG_INFO("ue3_shader_prebuild: {}: {} shader records, {}, {:.0f} ms", path.string(), records.size(),
   ```

   User names, custom install locations, and mod paths may consequently appear in logs users attach to public issues. Log paths relative to a known game root or log only a filename plus a stable non-identifying ID; scrub paths in existing report bundles.

7. **P2 — Incompatible stage-cache backups can accumulate indefinitely. Confidence: likely.** On a cache incompatibility the old stage store is renamed to a timestamped `.incompatible-*` file, and the PR notes explicitly say it is retained. Add a bounded cleanup/retention policy (or a user-visible cache management control) so repeated driver/build changes cannot consume unbounded disk space. Do not delete the active cache while a pipeline library still maps it.

8. **P3 — The optional CSV backpressure guard does not actually bound its pending memory. Confidence: certain.** When the writer queue is over 64 MiB, `FlushCsv` returns before clearing `csv_buf_`; subsequent frame rows continue accumulating in that string:

   ```cpp
   if (csv_out_.size() > (64u << 20)) return;  // the writer is stuck: drop rather than grow without end
   csv_out_ += csv_buf_;
   ```

   Drop or truncate rows and clear the producer buffer when saturated, and test with a deliberately blocked/slow output device. The CSV is opt-in, so this is lower priority than the startup gate.

9. **P2 — Performance evidence is encouraging but not a controlled before/after for all use cases. Confidence: certain.** The PR notes report fast cached starts and a short Gears 3 sample with no >50 ms frames, but also state that not every level was played and the full installed corpus was not compiled through the driver in the cited earlier test. The authored notes list test/build results, but the PR head has no GitHub check runs reported. Before making this the default, independently compare the same scenes and hardware with the feature on/off for all three games: cold launch, warm launch, transitions, ordinary gameplay, alt-tab/exit, disk-full/cache-corrupt recovery, and driver update. Track startup time, peak memory, cache size, 1% lows, skipped draws, and crash/hang rate.

### Positive changes worth retaining if validated

- The wait-loop change in all three games samples the guest-write sequence before the completion check and waits on that sampled value, addressing a real lost-wakeup window. Keep it, but validate with stress tests around writes arriving immediately before/after the wait and verify it on Windows/Proton paths where those waits are active.
- The PR adds persistent cache integrity checks, corrupt/truncated-cache recovery, asynchronous pipeline-stage reuse, and a frame log that can separate renderer/game waits. These are useful when they fail open to live compilation and do not put filesystem work on the render thread.
- The launcher includes a ShaderPrebuild switch, so the long startup path is selectable; the unsafe default is the main product decision to revisit, not the existence of the option.
- No game package contents are added in the reviewed diff. The feature reads shaders from the user's locally installed game files and stores derived caches locally; keep release packaging rules from ever including those source packages or per-user cache/log files.

**Recommendation:** retain the frame-wait fix and continue testing the asynchronous/cache work. Before adopting the PR's current default behavior, make startup preparation opt-in (or provide a first-run consent choice), add a reliable timeout/cancel-to-live-fallback path, and bound memory, background I/O, cache retention, and CSV buffering. Run matched on/off gameplay tests across all three games. Current evidence does not support claiming it will improve SteamOS/Vulkan or that every game's gameplay pacing improves.

## Additional D3D12 implementation research: SteamOS/Proton and CrossOver/D3DMetal (2026-10-29)

This addendum turns the existing platform goals and issue reports into a concrete implementation and validation plan. It does not claim that either platform is already supported. Local source findings below are from the checked-out `C:\COGBox` tree; external implementation facts link to primary project/vendor sources.

### Project constraints that determine feasibility

The launcher currently sets `vk` true whenever `env.wine` is true, regardless of the saved API selection, and emits `--gow2_renderer_api=vulkan`. Its source comment explains the behavior: the tested Proton/Wine D3D12 path exited shortly after renderer startup, while Vulkan reached gameplay. This is an intentional compatibility fallback for the tested Proton setup, but because detection is generic Wine it also catches CrossOver. A CrossOver user cannot currently prove the D3D12 renderer by merely selecting D3D12 in the launcher: the launcher overrides that choice before launch. See `Gears2-Native/cogbox/src/gears_settings.cpp`, the `const bool vk = s.i("Api") == 1 || env.wine;` decision and adjacent comment.

The game-side API selection is real and conditional: `Gears2-Native/src/layer0_xenos/gpu_system.cpp` constructs the Vulkan SDK provider only when `gow2_renderer_api` is `vulkan`, while `Gears2-Native/src/layer0_xenos/renderer/shadow_renderer.cpp` chooses a Vulkan or D3D12 backend from that same setting. The D3D12 implementation is therefore an existing backend that can be tested through a compatibility layer; it is not a request to implement a new native Metal renderer.

The D3D12 backend explicitly calls `D3D12CreateDevice` requesting feature level 12.0 and then rejects the device unless `CheckFeatureSupport(D3D12_FEATURE_SHADER_MODEL)` reports Shader Model 6.6. It logs the queried D3D12 runtime and SM version. This strict gate is material: neither a successful Windows build nor the existence of D3DMetal/VKD3D proves that a specific Apple GPU, SteamOS image, driver, or translation-layer version provides every feature COGBox uses. Do not spoof the reported feature level/model to get past this check. If a lower capability tier is desired, first audit generated DXIL and all feature-dependent renderer paths, then implement and validate an explicitly lower tier.

The CMake setup bundles the Agility SDK `D3D12Core.dll` under `<exe>\\D3D12\\` and copies DXC's `dxcompiler.dll`/`dxil.dll` beside the game executable. That is intended to give Windows 10 the runtime needed for SM 6.6. On Wine-derived runtimes, test these files as a compatibility variable: determine whether side-loading the bundled Agility core changes which D3D12 implementation is reached and whether DXC library loading/signing works in the bottle. Do not ship a replacement `d3d12.dll` or `dxgi.dll` that shadows Proton/CrossOver's compatibility implementation. Preserve the Windows behavior unless a platform-specific packaging change is justified by reproducible tests.

### What the compatibility layers provide—and what they do not

**SteamOS/Proton D3D12 path:** Proton implements Windows D3D12 through vkd3d-proton, which translates D3D12/DXIL behavior to Vulkan. The Linux driver and Vulkan capabilities are consequently part of the D3D12 path even though COGBox selects its D3D12 backend. Valve points D3D12 users to vkd3d-proton's requirements. Current vkd3d-proton documentation calls for a modern Vulkan implementation and required extensions/features; its current profile material distinguishes a baseline from higher “optimal” feature sets. SM 6.6 support is implemented in vkd3d-proton, but that does not remove the need for the required Vulkan capabilities or establish that every SteamOS/driver combination exposes them. AMD RADV is an especially relevant target for Deck testing; test on actual SteamOS rather than extrapolating from a desktop Linux distribution. [Valve Proton requirements](https://github.com/ValveSoftware/Proton/wiki/Requirements), [vkd3d-proton README](https://github.com/HansKristian-Work/vkd3d-proton/blob/master/README.md), [vkd3d-proton profiles](https://github.com/HansKristian-Work/vkd3d-proton/blob/master/profiles/PROFILES.md), [vkd3d-proton changelog](https://github.com/HansKristian-Work/vkd3d-proton/blob/master/CHANGELOG.md).

**CrossOver on macOS D3D12 path:** CodeWeavers documents D3DMetal as a CrossOver graphics backend for DirectX 11 and DirectX 12; DXVK is for D3D10/11, and DXMT is a D3D11 implementation. Thus the relevant experiment is COGBox's existing D3D12 backend in a clean 64-bit CrossOver bottle with D3DMetal selected. Do not select DXVK or DXMT expecting them to translate this renderer's D3D12 calls. D3DMetal availability is not proof that COGBox starts: the project's generic-Wine launcher override and the issue #40 Vulkan/provider startup path must be addressed or isolated first. CrossOver's optional “DLSS” toggle is documented as MetalFX-backed and only takes effect when the application itself enables DLSS; it is not proof that COGBox's DLSS integration, vendor SDK, motion vectors, or D3D12 upscaler path works on Mac. [CodeWeavers graphics backends](https://support.codeweavers.com/advanced-settings-in-crossover-mac), [CrossOver user guide](https://support.codeweavers.com/en_US/crossover-mac-user-guide), [CrossOver changelog](https://www.codeweavers.com/crossover/changelog).

Apple's Game Porting Toolkit and Metal Shader Converter document DXIL-to-Metal conversion and Shader Model features, but those native-porting tools are feasibility context only. They do not certify that CrossOver's D3DMetal accepts COGBox's particular DXIL, SM 6.6 usage, descriptor access pattern, Agility SDK runtime, or synchronization behavior. Likewise, a macOS Vulkan SDK/MoltenVK version is not the version supplied by a CrossOver bottle and cannot be used to infer D3DMetal support. [Apple Game Porting Toolkit](https://developer.apple.com/games/game-porting-toolkit), [Apple Metal Shader Converter](https://developer.apple.com/metal/shader-converter/).

### Priority implementation plan

1. **P0 — Make runtime policy explicit without regressing Proton.** Replace the single generic-Wine policy with explicit detected runtime information plus a user-selectable experimental route. Keep the current known-good SteamOS/Proton → COGBox Vulkan behavior as the default until D3D12 passes the full Proton gate. Add an explicit `D3D12 (experimental)` selection for a controlled test, and a CrossOver/D3DMetal profile if runtime detection can reliably identify it. Never silently rewrite a selected API: show requested API and actual backend separately. If runtime detection is uncertain, offer a user choice and default to the known-good route. This must be coordinated with `gears_settings.cpp`; a UI-only override is insufficient while `env.wine` still forces Vulkan.
2. **P0 — Trace and isolate API-specific initialization before changing the Vulkan check.** Follow the startup call chain from launcher arguments through rexglue/SDK provider creation, Vulkan loader/version validation, game-data-root parsing, GPU-system selection, presenter creation, and renderer device creation. Instrument the first Vulkan provider/loader call and log the exact component requesting Vulkan 1.3. Issue #40's message after removing `vulkan-1.dll` is a different failure stage, so do not infer that deleting the DLL fixes the renderer. Initialize/check Vulkan only on the Vulkan route if and only if that provider is truly optional to the chosen D3D12 runtime. If a shared SDK or menu bootstrap requires Vulkan even for the D3D12 route, make that layer API-neutral or create a D3D12-specific initialization path; do not bypass a requirement blindly.
3. **P0 — Add a small, privacy-safe graphics startup report.** On every run, log: requested API; effective API; provider/presenter/backend actually created; runtime classification (Proton, CrossOver, other Wine, Windows, unknown); D3D12 runtime/core path category (system vs bundled, without a personal absolute path); feature level; highest supported shader model; optional D3D12 feature probes; adapter vendor/device and driver/runtime versions; Vulkan loader/device/extensions only on the Vulkan/vkd3d route; executable architecture; title/TU. Add explicit phase markers so a failure says whether it happened before argument parsing, game-root validation, SDK provider initialization, D3D12 device creation, shader loading, or first present. Avoid username, home/install path, bottle name, or unredacted environment dumps in public logs.
4. **P1 — Make compatibility probes non-destructive and repeatable.** Provide a documented developer/advanced launch mode that selects D3D12 for one run while retaining the saved default and recording a fallback route. Do not automatically switch APIs mid-run after a partially created device; terminate cleanly and offer the alternate route on the next run. A “try D3D12” failure must preserve settings, logs, and game files and return the launcher to a usable state.
5. **P1 — Treat bundled Agility/DXC loading as a matrix, not an assumption.** For Windows, keep existing Agility behavior. For Proton and CrossOver, compare (a) current package as-is, (b) the runtime's normal D3D12 core with only DXC copied, and (c) a platform-supported runtime arrangement if vendor documentation allows it. Record loaded module paths and device-creation results. Do not delete or rename the bundled DLL as an end-user workaround; use a reproducible test package/configuration. Never bundle host compatibility DLLs from Proton or CrossOver into COGBox.
6. **P1 — Build a focused SteamOS/Deck test matrix.** Test on a retail Steam Deck with current stable SteamOS and current stable Proton, then Proton Experimental as a separate result. Test both the known-good Vulkan mode and the explicit experimental D3D12 mode. Record OS image, Proton build, Mesa/RADV version, GPU, API, and all capability probes. Run each game/TU through cold boot, warm boot, campaign/menu transition, checkpoint reload, 30–60 minutes of play, suspend/resume, alt-tab/overlay, and orderly exit. Include the reported SteamOS network-layer startup failure as its own runtime path; success of D3D12 device creation does not prove game initialization, networking, video playback, controller handling, or saves work.
7. **P1 — Build a focused CrossOver matrix.** Start with a clean 64-bit bottle on Apple Silicon, set bottle Graphics to D3DMetal, and use a launcher override that demonstrably passes D3D12. Record CrossOver/macOS version, Apple chip/GPU, bottle architecture, D3DMetal version, loaded D3D12 runtime, SM result, and first failing startup phase. Test current CrossOver release and one current supported macOS release; add an Intel Mac only if the chosen CrossOver release supports it. CrossOver 26.3's published changelog lists a D3DMetal 3.0 update; retest after CrossOver/D3DMetal changes because translation behavior can shift between versions. [CrossOver release history](https://www.codeweavers.com/crossover/changelog).
8. **P1 — Test all three titles and the actual renderer feature set.** On both platforms, test Gears 2, Gears 3, and Judgment separately across their supported title updates. Verify first present, opening video, menus, HUD, depth/stencil, occlusion, MSAA/sample-position fallback, shadows/lights, texture streaming, render scale, SMAA, and resolution changes. D3D12-only FSR/DLSS/XeSS must remain unavailable where their native SDK/device requirements are not met; CrossOver's MetalFX DLSS toggle should not be presented as COGBox DLSS support unless an end-to-end test demonstrates it. Track graphics correctness and feature fallback independently from launch success.
9. **P1 — Measure pacing and performance at matched settings.** Use identical scenes and resolution/render scale; capture COGBox's own CPU/GPU frame timings, external overlay timing, present mode, frame cap, 1% lows, and hitch counts. On Proton, test first with the compatibility layer's default frame limiting/caches, then change one factor at a time. vkd3d-proton documents `VKD3D_FRAME_RATE`; do not set it alongside COGBox's limiter while deciding whether COGBox's limiter is effective. Also compare cold and warm cache runs. Do not claim D3D12 is smoother than Vulkan from average FPS alone.
10. **P2 — Test caches per translation layer and machine.** Proton/vkd3d-proton normally maintains its own DXIL-to-SPIR-V/driver cache. Its documentation notes that application `ID3D12PipelineLibrary` contents can be a dummy cache while that internal cache is active; disabling the internal cache changes the role of the app library. Therefore PR #43's application pipeline cache may have limited or different benefit under Proton than on Windows. First measure Proton defaults; only then compare its documented `VKD3D_SHADER_CACHE_PATH=0` or `VKD3D_CONFIG=pipeline_library_app_cache` test modes. These are diagnostic comparisons, not default user launch options. Keep separate cache keys/locations for game/TU, renderer version, API, GPU/driver, and translation runtime; never distribute a universal driver PSO cache. D3DMetal caches also need separate validation and invalidation rules. [vkd3d-proton cache documentation](https://github.com/HansKristian-Work/vkd3d-proton/blob/master/README.md).
11. **P2 — Package only the components COGBox owns.** Keep COGBox-authored shaders and required licensed redistributables/notices under the existing release policy. Let Proton/CrossOver supply their translation layers and per-machine caches. Do not package leaked game content, game-derived guest shader caches, another user's pipeline library, Proton's `d3d12.dll`/`dxgi.dll`, or a CrossOver D3DMetal runtime. Test that the release zip preserves COGBox's expected DXC/Agility layout without shadowing the host's compatibility DLLs.
12. **P2 — Publish a clear support boundary.** Until the matrix passes, advertise Windows D3D12 as the supported target; SteamOS/Proton Vulkan as the known working compatibility route where confirmed; SteamOS D3D12 and CrossOver/D3DMetal as experimental. Include a short diagnostic bundle guide that asks for the phase-marked log and runtime versions and reminds users to remove usernames and absolute paths before posting.

### Acceptance gates and evidence required before changing defaults

Do not make D3D12 the SteamOS default or declare Mac support until each of the three games reaches gameplay and exits cleanly on target hardware in repeated runs, with no Vulkan 1.3 false failure on a D3DMetal-only route, no silent API override, no missing critical renderer feature, and no regression in the known-good Proton/Vulkan route. Require a minimum repeated-run success rate agreed by the project (recommended: 20 clean launches per game/runtime configuration), a sustained gameplay session, and a before/after frame-time comparison. Record unresolved visual, input, audio, network, video, and save limitations individually. These are proposed release gates, not results already achieved.

For the first triage report, capture one run per game and route with: exact launcher API choice; exact runtime/version; device and driver; COGBox log from process start to exit; whether the bundled `D3D12Core.dll` was loaded; D3D12 feature-level and SM probes; first failure phase; and a matching Vulkan/known-good run. CrossOver's native bottle logs and Proton's logs may contain personal paths, so redact before attaching publicly.
